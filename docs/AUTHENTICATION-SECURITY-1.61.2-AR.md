# إدارة الدخول والتسجيل من الشبكات المشتركة — 1.61.2

حلّت هذه السياسة محل سياسة 1.61.1 التي كانت تجمع المستخدمين في حد دخول صغير لكل عنوان IP. الحماية داخل الإضافة وتنتقل بتحديثها على الاستضافة. لم يجر تحديث الاستضافة ضمن هذا العمل.

## الحدود الحالية

| العملية | الحد الفردي | حد أمان الشبكة |
|---|---|---|
| الدخول عبر الموقع وWordPress وXML-RPC | 10 محاولات لكل **حساب + IP** خلال 15 دقيقة | 300 محاولة خلال 15 دقيقة |
| REST Application Passwords | 120 طلب مصادقة لكل **حساب + IP** خلال دقيقة | 1200 طلب مصادقة خلال دقيقة |
| التسجيل الجديد | 5 محاولات لكل **بريد + IP** خلال ساعة | 100 محاولة خلال ساعة |

كل الحدود نوافذ ثابتة، وتحتسب الطلبات الناجحة والفاشلة. التسجيل مستقل عن الدخول وعن كلمات مرور التطبيقات. أسماء المستخدمين والبريد للحساب المعروف تُحوّل إلى معرّف الحساب نفسه، لذلك لا يسمح التبديل بينهما بتجاوز الحد. لا تُخزن هذه الأسماء أو عناوين IP كنص في جدول الحدود؛ المفاتيح HMAC وتُحذف بالسياسة المجدولة الموجودة.

إذا استنفد المستخدم «أ» محاولاته من شبكة مشتركة، يستمر المستخدم «ب» في الدخول، كما يستطيع زائر جديد التسجيل ببريد مختلف. تكرار ضرب حساب مقيّد بالفعل لا يستهلك حد الشبكة العام: يفحص النظام الحد الفردي أولًا ويرفض الطلب قبل الوصول إلى حد الشبكة أو فحص كلمة المرور.

يبقى حد الشبكة الأوسع لمنع تجاوز الحماية بمحاولة أسماء حسابات كثيرة. لذلك ليست الشبكات المشتركة مستثناة دون حدود: قد يتأثر الجميع مؤقتًا إذا تجاوز مجموع المحاولات المؤهلة حد الأمان الكبير. لا يوجد استثناء سري بترويسة أو عنوان URL. المستخدم نفسه من شبكة أخرى لا يُقفل عالميًا.

طلبات الجلسات القائمة عبر الكوكيز لا تستهلك هذه الحدود. يستمر منع الحساب الموقوف وغير المؤكد، وتستمر أخطاء 429 وRetry-After عند تجاوز الحد و503 عند تعطل التخزين. لا يتغير مخطط البيانات. استُخدمت مساحة مفاتيح جديدة حتى لا يظل حد الشبكة القديم البالغ 10 محاولات فعالًا بعد التحديث؛ تنتهي سجلاته القديمة وتُنظف كالمعتاد.

## الاستضافة

عنوان الزائر الصحيح ضروري خلف Cloudflare أو بروكسي. يستخدم النظام ClientAddress الموجودة، ويتجاهل X-Forwarded-For ما لم يكن الوكيل المباشر ضمن نطاقات `adc_trusted_proxy_cidrs` المعتمدة. لا يُنصح باستثناء شبكة كاملة من الحماية؛ اضبط الوكيل الصحيح وراقب معدل الاستخدام عند نشر الموقع. لا يمكن لهذه السياسة وحدها منع هجمات موزعة من عناوين كثيرة.

حزمة الإضافة هي 1.61.2. زومنت أرقام إصدار القالب فقط مع متطلبات أداة بناء الحزم؛ لا تغيير تشغيلي في القالب.

## التحقق

- اختبارات دون قاعدة بيانات: العزل بين حسابات الشبكة نفسها، توحيد اسم الحساب والبريد، عدم استنزاف الشبكة عبر حساب محظور، استقلال التسجيل، انتهاء النوافذ، الترويسات المزورة، حد الشبكة ضد تدوير الحسابات، وحدود REST وفشل التخزين.
- اختبارات WordPress/MariaDB المعزولة: دخول مستخدم ثان من العنوان نفسه بعد تقييد الأول، وإنشاء حسابَي عميل حقيقيين ببيانات صناعية من الشبكة نفسها، وعدم استهلاك التسجيل ميزانية الدخول، واستمرار ضوابط XML-RPC والبريد والتعليق وأخطاء HTTP وREST.
- اختبار HTTP مستقل يؤكد نجاح دخول المستخدم الثاني من نفس عنوان خادم الاختبار بعد إرجاع 429 للأول. اختبارات التسجيل شغّلت حارس التسجيل وخدمة إنشاء الحساب الفعلية؛ لم تنفذ واجهة التسجيل كاملة في متصفح.

استُخدمت MariaDB مستقلة على loopback والمنفذ 33369 و`database-runner.php --isolated` مع `ADC_AUTH_ONLY=1`. لا يقرأ هذا المسار wp-config.php المحلي ولا يتصل بقاعدة الموقع. تُحذف قاعدة الاختبار بعد التشغيل ويُوقف الخادم المؤقت. اختبار الترجمة القديم المتعطل المذكور في تقرير 1.61.1 لم يُعد تشغيله، وليس من اختبارات قبول هذه الميزة.

النتيجة: **192 فحصًا ناجحًا**: 46 دون قاعدة بيانات لحارس المصادقة، و34 على WordPress/MariaDB وHTTP المعزولة، و112 فحصًا سابقًا للصلاحيات والأموال والتسعير ولغة النشرة وعقد الاستجابة. اجتاز PHP syntax الملفات الثمانية المتأثرة، واجتاز git diff --check. أكد SHOW DATABASES بقاء القواعد النظامية فقط قبل إيقاف MariaDB الاختبارية.
