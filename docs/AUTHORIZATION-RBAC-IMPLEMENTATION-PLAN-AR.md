# الخطة التنفيذية لتوحيد الصلاحيات والتحكم بالوصول

**المشروع:** Auto Dealership Core — WordPress / PHP  
**الحالة:** المرحلة 1 مكتملة فنيًا؛ اكتمل في المرحلة 2 خط أساس المصدر، وربط القدرات بالأفعال، وتعداد REST و`admin_post` و`wp_ajax`، ومراجعة أسطح التقارير والتصدير ذات الأولوية، وجرد حقول مخطط جداول الإضافة، واختبار effective access ببيانات مراجعة اصطناعية لفرعين عبر الخدمات وREST v1/v2. أكد المستخدم في 2026-10-23 أن الموقع المحلي هو بيئة إنتاج ويريد اختبارات فعلية؛ لذلك تُعامل قاعدة الموقع وبياناتها كإنتاج. بيانات المراجعة الاصطناعية ليست عينة تشغيلية ممثلة، لكنها موجودة في قاعدة الإنتاج ولا يجوز حذفها أو تعديلها ضمن الاختبارات دون موافقة صريحة. تظل المرحلة 2 مفتوحة لأن تتبع الحقول لكل مخرج/استعلام واختبارات الرفض الشاملة واعتمادات سياسة وخصوصية تخص مالكيها لم تكتمل.
**تاريخ الإعداد:** 2026-10-22  
**النطاق:** الأدوار، القدرات، نطاق الوصول، تفويض الموارد، واجهات API والخدمات، تدقيق العمليات، والترحيل الآمن

> **سياق المنتج والعملاء:** المنتج قالب WordPress وإضافة يمكن لشركات مختلفة تثبيتهما على مواقعها؛ هذا لا يعني تلقائيًا أن شركات متعددة تشترك في تثبيت أو قاعدة بيانات واحدة. الخطة توثق تثبيتًا واحدًا في كل مرة، ولكل شركة عميلة ملف سياسة وقرار خاص بموقعها، ولا تنتقل موافقة عميل إلى آخر. `BranchScope` نطاق الفروع داخل تثبيت العميل، وليس ميزة عزل شركات مستقلة. لا تثبت هذه الخطة دعم SaaS متعدد المستأجرين أو تشغيل عدة شركات داخل موقع/قاعدة مشتركة؛ إن طلب عميل نمطًا كهذا فيلزم تقييم واختبار منفصلان قبل إعلانه مدعومًا.

> هذه الوثيقة تنظّم المتطلبات الواردة في المقترح المرفق في خطة قابلة للتنفيذ والمراجعة، وليست تقرير التدقيق نفسه. اكتمل الجرد الفني للمرحلة 1 ووُثقت نتائجه في التقرير المرتبط؛ ولا يعني ذلك وجود اختبار سلوكي مستقل لكل معالج أو مصفوفة IDOR كاملة.

## سجل التنفيذ

- **لقطة تاريخية لقاعدة `wp-autobrands` (2026-10-23):** وثقت 23 مستخدمًا (المسؤول و22 حساب مراجعة اصطناعيًا)، وبيانات مراجعة اصطناعية أخرى. كانت الخطة تصنفها سابقًا كقاعدة تطوير بسبب عنوان الموقع المحلي؛ صحح المستخدم هذا التصنيف وأكد أن الموقع المحلي هو بيئة إنتاج. لا تُعامل الأعداد أو الحالات التاريخية كحالة راهنة.
- **تصحيح البيئة واختبار القراءة الإنتاجي (2026-10-23):** بناءً على تأكيد المستخدم، تُعامل قاعدة الموقع كإنتاج. فحص `database-runner.php --inspect` للقراءة فقط أكد PHP 8.2.12 وWordPress 7.1.3 وMariaDB 10.4.32 وإصداري المخطط/الأدوار `1.29.0`/`1.65.2`؛ واستعلام قراءة فقط وجد 22 اسم دخول يبدأ بـ`rbac_review_`. قبل تشغيل WordPress الكامل، كانت علامات ترحيلات الصلاحيات الأربع مكتملة، وإصدارات المخطط/الأدوار مطابقة، وقدرات الإضافة المطلوبة موجودة للمسؤول، ومهمة تحرير المطالبات القديمة مجدولة؛ لذلك لم يكن متوقعًا أن تنفذ مسارات الإقلاع كتابة ترحيل أو جدولة جديدة. شُغلت قراءة GET فعلية من موجه REST في تطبيق الموقع باستخدام حسابات المراجعة الموجودة، مع تعطيل WP-Cron لهذه العملية وعدم تنفيذ POST/PUT/PATCH/DELETE. نجحت **16 حالة** عبر v1/v2: المبيعات ضمن المالك، ومديرو الفرع وخدمة العملاء ضمن الفرع، وإخفاء حقول البريد/المدينة والحملة/المنصة والمنشئ لسجل `new` غير المسند، ورفض Auditor والمخزون لقائمة الفرص؛ أعاد الطلب غير المسجل 401. لم تعرض نتائج الاختبار أي محتوى عميل أو معرفات سجلات. أعاد التسويق 200 بقائمة خالية، لذا لا تثبت هذه العينة سماح القراءة الإيجابي لتسويق على سجل قائم. لم تُنشأ أو تُعدّل أو تُحذف حسابات أو سجلات أعمال. يظل الاختبار الحقيقي محدودًا بحسابات مراجعة موجودة وبالبيانات التي أعادتها القراءة، وليس اعتمادًا للسياسة أو إثباتًا شاملًا لكل الحقول.
- اجتازت إعادة تشغيل `ADC_DATABASE_SCENARIOS_ONLY=1` **968 اختبارًا** في قاعدة عشوائية منفصلة `adc_verify_*` أُنشئت وحُذفت على خادم قاعدة البيانات نفسه؛ يؤكد المشغل أن بيانات قاعدة الإنتاج المصدر لم تتغير.
- أضيفت أولًا اختبارات خدمة داخل قاعدة معزولة تثبت أن موظف المبيعات يرى فرصه فقط، ومدير الفرع/خدمة العملاء يرى سجلات فرعه فقط، وأن الفرع المقابل والأدوار غير المخولة لا تظهر لها سجلات؛ اجتاز تشغيل تلك الجولة **953 فحصًا** قبل إضافة تأكيد HTTP.
- استُكملت هذه التغطية بحد HTTP حقيقي لقائمة فرص CRM: اختُبرت REST v1 وv2 للمبيعات والموظف الآخر في الفرع نفسه ومديري الفرعين وخدمة العملاء والمدير العام، مع التأكد من ظهور سجلات الفرع/المالك المطلوبة وحجب السجلات المستبعدة. كما اختُبرت أدوار لا تملك قراءة CRM للتأكد من رفض الطلب أو إرجاع قائمة فارغة دون تسريب سجلات. اجتاز تشغيل `ADC_DATABASE_SCENARIOS_ONLY=1` **968 فحصًا**؛ أُعيد تعطيل الفرع بعد الاختبار، وحُذفت قاعدة الاختبار وبقيت قاعدة المصدر دون تغيير.
- بدأ التنفيذ على مراحل بعد طلب المستخدم، مع الحفاظ على آليات الأدوار والتخصيصات والنطاق القائمة.
- أُضيفت في الإصدار 1.65.2 قدرة `adc_assign_marketing_leads` إلى الأدوار الافتراضية لمدير المبيعات والمدير العام، وإلى كتالوج تخصيص الدور/المستخدم. لم تُمنح افتراضيًا للتسويق.
- حُميت عمليتا إسناد العميل وتحرير إسناده في الخدمة وREST بهذه القدرة؛ تسمح القدرة الجديدة وحدها بإسناد/تحرير العملاء ذوي المصدر `marketing` فقط، بينما بقيت القدرات القديمة `adc_manage_branch_leads` و`manage_options` مقبولة مؤقتًا للحفاظ على السلوك السابق. يظل فحص نطاق الفرع داخل الخدمة.
- نجحت فحوص PHP و52 اختبارًا محليًا دون قاعدة بيانات. ثم نجح `database-runner.php --isolated 33387` على خادم MariaDB مؤقت: اكتملت 768 فحوص قاعدة البيانات وHTTP، بما فيها السماح بإسناد عميل تسويقي عبر REST بالقدرة الجديدة وحدها ورفض إسناد عميل غير تسويقي بها. أزيلت قاعدة الاختبار وأُوقف الخادم، ولم يُتصل بقاعدة بيانات الموقع.
- بدأ تدقيق المرحلة 1 للقراءة فقط ووُثقت نتائجه الأولية في [تقرير التدقيق المرحلي](./AUTHORIZATION-RBAC-AUDIT-AR.md). شمل جردًا ساكنًا للأدوار والقدرات وREST وحراس الخدمات، واستعلامًا تجميعيًا محليًا لم يكشف تعريفات أدوار مخصصة أو تجاوزات مستخدم فردية. رُصدت فجوات في ترحيل صلاحيات التسويق، وتغطية كتالوج القدرات، واتساق REST مع خدمة عرض فرص التسويق؛ تفاصيلها وحدود التحقق موثقة في التقرير.
- عولجت فجوات التسويق الثلاث المحددة: الترحيل يحترم تعريف الدور المخصص، والكتالوج يعرض القدرات الخمس المترجمة، وحارس REST يسمح لمستخدم التسويق بعرض سجلاته المنشأة فقط. لم تُغيّر حدود الاعتمادات المالية أو قيود الفروع أو الوصول القديم.
- أثناء تتبع سجل الأنشطة، عولج عدم اتساق إضافي: صارت قدرة نشاط التسويق تسمح بإضافة أنواع النشاط غير البيعية إلى سجل تسويقي أنشأه المستخدم ضمن فرعه فقط، مع اختبار منع السجلات المنشأة من غيره. أضيفت قدرة العرض التسويقية كذلك إلى بوابة قراءة سجل الأنشطة.
- نجحت مجموعة `database-runner.php --isolated` كاملة على خادم MariaDB مؤقت فارغ، بما فيها اختبار الترحيل المخصص وتطابق الكتالوج واختبارات REST لقائمة الفرص وسجل الأنشطة وإضافتها ضمن قيد المنشئ. كما نجحت 52 فحوص تفويض دون قاعدة بيانات وفحوص PHP. أزيلت قاعدة الاختبار والخادم المؤقتان، ولم تُستخدم قاعدة بيانات الموقع. أما فحص التوطين الكامل فيكشف تسميات سابقة غير مسجلة في `Navigation.php` و`OutboxPage.php`، وليس التسميات الجديدة.
- في دفعة المشتريات، وُحّد تسجيل صفحة تكاليف الاقتناء مع تفويضها الموجود: يقبل عنصر التنقل قدرة العرض أو الإدارة، وتستخدم الصفحة أول قدرة يملكها المستخدم عند تسجيلها. أضيف اختبار قائمة لمستخدم الإدارة فقط، وأُدرجت صفحة الاقتناء في مسارات موجه HTTP الاختباري ثم تحقق اختبار HTTP من فتحها؛ كان 404 السابق ناتجًا عن غياب الصفحة من قائمة الموجه الاختباري. نجحت **54 فحصًا** في تشغيل `ADC_PURCHASING_ONLY=1` مع قاعدة اختبار مؤقتة وفارغة، وأزيلت بعد التشغيل دون استخدام قاعدة الموقع. لم تُمنح أي قدرة جديدة ولم يتغير نطاق الفروع.
- في مراجعة سطح AJAX/قراءة المخزون، عولج كشف مؤشرات وجود VIN ومصادر Onyx من فروع أخرى في `InventoryIdentityLookup`: صارت مطابقة السجلات المرتبطة حسب فرع المركبة، وغير المرتبطة حسب المستودع المعيّن، قبل حساب الوجود والالتباس واختيار المطابقة. بقيت دالة `sources()` المستخدمة في التحقق عند الحفظ دون تغيير. نجحت **88 فحصًا** في `ADC_ONYX_ONLY=1` على قاعدة معزولة، بما فيها اختبار منع الكشف بين الفروع واستمرار القراءة داخل الفرع وبقاء وصول المسؤول. الاختبار الحالي على مستوى الخدمة وليس HTTP، وأزيلت قاعدة الاختبار دون استخدام قاعدة الموقع.
- تم تتبع معالج `adc_move_lead_stage` من AJAX إلى `LeadService::update_stage()`، ولم تظهر فجوة تفويض: ترفض الخدمة المستخدم الذي لا يملك قدرة إدارة العملاء، وتطبق فحص الملكية ونطاق الفرع. أضاف اختبار HTTP محاولة تغيير مرحلة عميل محتمل أنشأه مستخدم التسويق، وتحقق من **403** وعدم تغير المرحلة. نجح تشغيل `database-runner.php --isolated` كاملًا، وأزيلت قاعدة الاختبار المؤقتة دون استخدام قاعدة الموقع.
- في مراجعة قراءة بوابة العملاء، لا تعيد `Portal::poll()` تفاصيل المحادثة إلا بعد تحقق الخدمة من الملكية أو صلاحيات الموظف ونطاقه، وتحجب الرسائل الداخلية عن العميل؛ ويتطلب `LiveChat::status_endpoint()` تسجيل الدخول وnonce وإمكانية الوصول للمحادثة، ويعيد حالة حضور محدودة. لم تظهر فجوة تفويض. توجد اختبارات متصفح لهذه الأسطح، لكنها لم تُشغّل في هذه الدفعة.
- في متابعة معالجات AJAX العامة، أضيف اختبار HTTP مجهول لمسار `car_dealer_lead`: nonce غير صالح لا يكتب سجلات، والطلب الصحيح ينشئ سجلاً واحداً دون إعادة المعرفات الداخلية، وإعادة الطلب بالمفتاح نفسه لا تكرر السجلات. نجحت الاختبارات الثلاثة ضمن تشغيل التكامل المعزول الكامل. كما شمل التتبع المقارنة وحاسبة التمويل والاشتراك التسويقي، دون تأكيد فجوة تفويض في المراجعة المحدودة.
- أضيفت الآن اختبارات HTTP مباشرة للاشتراك والمقارنة وحاسبة التمويل: تحقق nonce، واشتراط الموافقة الصريحة قبل حفظ اشتراك معلق، وقبول مركبة عامة ورفض غير متاحة، وقبول مدخل حاسبة صحيح ورفض سعر مشوه. نجحت المجموعة المعزولة الكاملة ولم تُستخدم قاعدة الموقع. لم يتغير سلوك الإنتاج؛ التعديل في موجه الاختبار وتغطية التكامل.
- اكتملت الخطوة التالية باختبار HTTP لمعالج `adc_lookup_vin`: رفض nonce غير صالح، وصول مستخدم الفرع المعيّن إلى المركبة ومصدر Onyx المرتبط، حجب مؤشرات الوجود والتفاصيل عن مستخدم فرع آخر، اختبار حجب مصدر Onyx غير المرتبط والمقيد بتعيين المستودع، واستمرار وصول المسؤول العام. نُظفت بيانات الاختبار قبل بقية السيناريوهات. نجح تشغيل التكامل المعزول الكامل دون استخدام قاعدة الموقع.
- أضيفت تغطية HTTP مباشرة لمعالج `admin-post` الخاص بتصدير التسويات المالية: رفض مستخدم بلا `adc_view_finance`، ورفض nonce غير صالح، والتحقق من ظهور بيع الفرع المخول مع استبعاد بيع فرع آخر. نجح تشغيل `database-runner.php --isolated` الكامل؛ أزيلت قاعدة الاختبار ولم تُستخدم قاعدة الموقع. رُفع حد انتظار طلبات HTTP في أداة الاختبار من 5 إلى 15 ثانية لتجنب انتهاء المهلة خلال التشغيل المعزول على Windows؛ لا تغيير إنتاجي.
- أضيفت تغطية HTTP لمعالج تصدير التقرير التشغيلي: رفض دور لا يملك `adc_view_reports`، ورفض nonce غير صالح وتواريخ غير صالحة، والتحقق من قصر صفوف المبيعات على الفرع المعيّن، ومن تحييد صيغة جدول في اسم الفرع وعدم كشف بيانات اتصال العميل أو هوية المركبة. نجحت مجموعة التكامل المعزولة كاملة، ولم تُستخدم قاعدة الموقع أو تُجرَ تغييرات إنتاجية.
- تم تتبع معالجي مستندات Onyx للرفع والتنزيل: يعيد التنزيل فحص القدرة ونطاق الفرع بعد nonce، ويتحقق checksum للملف؛ ويفرض الرفع القدرة والنطاق والتحقق من المصدر والمبالغ والتدقيق عبر الخدمة. أضيفت اختبارات HTTP فعلية للتنزيل والرفع multipart، تشمل النجاح داخل الفرع، ورفض nonce، ورفض المبيعات بلا قدرة اعتماد، ومنع التنزيل والرفع عبر الفروع، واستمرار وصول المسؤول. نجحت مجموعة مساحة العمل/Onyx المعزولة (**362 فحصًا**) دون استخدام قاعدة الموقع.
- اكتمل تتبع `IntegrationPage` لمعالجي `adc_set_integration_route` و`adc_reconcile_integration` باختبارات HTTP للصلاحية وnonce وتغيير الحالة والتدقيق وعدم جدولة مطابقة لإيصال غير موجود. كشف الاختبار أن `sanitize_key()` يحذف النقطة من مفتاح الحدث `sale.approved`؛ صُحح التنظيف في المعالج مع استمرار حصر القيم المقبولة في `IntegrationActivation`. نجح تشغيل `database-runner.php --isolated 43138` كاملًا بعد الإصلاح، دون استخدام قاعدة الموقع.
- اكتملت تغطية HTTP لمعالج إعادة محاولة Outbox: الرفض بلا `adc_manage_outbox` أو مع nonce غير صالح، إعادة حدث فاشل مخوّل مع إعادة ضبط المحاولات وتسجيل التدقيق، واستمرار الحماية من إعادة الرسائل البريدية الأقدم من 24 ساعة. نجح التشغيل المعزول الكامل وأزيلت قاعدة الاختبار.
- اكتملت تغطية معالجات البيانات المرجعية لإنشاء علامة تجارية وموقع وتغيير حالة العلامة عبر HTTP. يفرض `ReferenceService` قدرة `manage_options` داخل الخدمة؛ رُفضت الطلبات غير المخولة وnonce غير الصالح دون تغيير، وأثبتت الطلبات المخولة الإنشاء/التعطيل مع تسجيل التدقيق، وتقييد الموقع للفرع المرسل. اكتملت كذلك مراجعة `InventoryIdentityPage` للاستلام والفحص: فرض القدرة ونطاق الفرع داخل `VehicleIntakeService`، واختبارات HTTP ترفض nonce غير الصالح، وموظف الفرع الآخر، ودور المالية، دون كتابة سجلات. نجحت المجموعة المعزولة الكاملة واختبارات `ADC_DASHBOARD_ONLY=1` (**38 فحصًا**)؛ أزيلت بيانات الاختبار ولم تُستخدم قاعدة الموقع. الخطوة التالية مواصلة جرد معالجات `admin-post` الأخرى والمسارات الحساسة وواجهات القراءة غير المغطاة.
- اكتملت مراجعة معالجات `CatalogPublishingPage` الثلاثة المرتبطة بحفظ صفحة المركبة، وتغيير حالة الصفحة، وحفظ التصنيف. أضيف اختبار HTTP لصلاحية الخدمة وnonce لإنشاء التصنيف، ولرفض تغيير الحالة دون صلاحية أو nonce صالح، وللتغيير المخول إلى السلة ثم الاستعادة إلى مسودة مع التدقيق.
- اكتملت مراجعة `OfferPublishingPage` و`OfferPublishingService`؛ أضيفت اختبارات HTTP ترفض إنشاء العرض أو تغيير حالته دون صلاحية وnonce صحيحين، وتثبت الإنشاء المخول لمسودة مدققة مرتبطة بسيارة متاحة، والتغيير إلى السلة والاستعادة الآمنة إلى مسودة. امتدت تغطية HTTP إلى حفظ محتوى الموقع: رفض دور غير إداري وnonce غير صالح دون تغيير الخيار، ونجاح الحفظ الإداري مع حدث التدقيق. نجحت مجموعة `ADC_CATALOG_ONLY=1` (**78 فحصًا**) واختبارات `ADC_PRODUCT_ONLY=1` (**138 فحصًا**) بعد التغيير، وأزيلت قواعد الاختبار دون استخدام قاعدة الموقع.
- بدأت متابعة `SiteContentPage::submit()` لنقل المحتوى: تأكد وجود حارس `manage_options` قبل فحص nonce، وبدأ تتبع `ContentTransfer` للتصدير ورفع الحزمة وتطبيق المعاينة. الخطوة التالية إضافة تحقق HTTP لرفض الصلاحية/nonce وعدم تغيير المحتوى عند فشل الاستيراد، مع مراجعة القيود والمعاينة وتنظيف الملف المؤقت.
- **تصحيح جرد المصدر أثناء المرحلة 2:** تعداد `Routes.php` الحالي هو 56 استدعاء تسجيل (55 مسارًا نصيًا مميزًا)، و65 زوج طريقة/مسار (14 GET و3 PATCH و48 POST)، ويسجلها helper في namespace `v1` و`v2` (130 تسجيلًا). أما hooks الحالية فهي 97 `admin_post` (85 تسجيلًا حرفيًا و12 مشتقًا من قائمتين ديناميكيتين) و22 `wp_ajax`؛ المجموع 119 اسم hook مميزًا، منها تسجيلان `admin_post_nopriv` و7 تسجيلات `wp_ajax_nopriv` (9 إجمالًا). لذلك أرقام 36 مسارًا/72 تسجيلًا و85 admin-post في الأسطر التاريخية أدناه تصف جردًا سابقًا غير مكتمل للنقاط الديناميكية؛ لا تستخدم كعداد حالي. تتبع المرحلة 1 الثابت وحالات الاختبار السابقة محفوظة، ولا يعني التعداد وجود اختبار رفض مستقل لكل hook أو لكل تبديل معرف/فرع.
- وثّق التدقيق مخاطرة متانة محددة في ترحيلات القدرات: تُحدَّث علامات الإصدار بعد الكتابات دون فحص كامل لنتائج كل تعديل، ما قد يحجب فشلًا جزئيًا. كما يعتمد تراجع تحديثات الأدوار/المستخدمين عند فشل التدقيق على قابلية جداول WordPress الأساسية للمعاملات، ولا تتحقق الإضافة من محركاتها. لم يثبت وقوع فشل تشغيلي؛ لا تُغيّر سياسة المنح ضمن معالجة هذه المخاطر.
- اجتاز فحص BranchScope غير المتصل **52 تحققًا** في هذه الشريحة. لم تُجرَ اتصالات بقاعدة الموقع؛ وستُختبر معالجة مخاطر الترحيل في قاعدة معزولة ضمن مرحلة التنفيذ المناسبة.
- **بوابة المرحلة التالية:** مراجعة هذا التقرير والخطة واعتماد المالك، ثم حسم أولوية معالجة موثوقية الترحيلات وتوسيع اختبارات الرفض/IDOR. لم يبدأ تغيير إنتاجي جديد في هذه الشريحة.

## 1. الملخص التنفيذي

الهدف هو الوصول تدريجيًا إلى نموذج تفويض قابل للتفسير والاختبار، تكون فيه صلاحية المستخدم ناتجة عن اجتماع:

```text
هوية المستخدم الموثقة
  → الدور والقدرات الفعلية
  → نطاق الوصول (Scope)
  → ملكية المورد وحالته
  → قواعد العمل وحدود الاعتماد
  → تفويض الخدمة
  → تفويض REST/API
  → تصفية البيانات المعروضة
  → واجهة ملائمة للصلاحيات
  → سجل تدقيق
```

لا يعني ذلك استبدال نظام WordPress أو إعادة كتابة الإضافة. المطلوب هو فحص البنية الحالية، ثم سدّ فجواتها بأقل تغييرات متوافقة ممكنة، مع الحفاظ على الوظائف التجارية، والأدوار المخصصة، والتخصيصات الفردية، وعقود API، وبيانات الموقع.

## 2. سياق المشروع والقرارات الأولية

يُظهر الفحص الاستطلاعي المحدود وجود بنية قائمة، لذا يجب البناء عليها لا إنشاء نظام موازٍ:

- تعريفات أدوار وقدرات داخل `src/Core/Capabilities.php`، تتضمن أدوارًا مثل `dealership_marketing` و`dealership_sales` و`dealership_finance` و`dealership_auditor`، وعدة ترحيلات قدرات سابقة.
- إدارة تخصيص صلاحيات المستخدم داخل `src/Admin/UserPermissions.php`، باستخدام منح/منع WordPress، مع حماية إدارية وإبقاء قيود الفروع قائمة.
- وثيقة قائمة لصلاحيات الأدوار والمستخدمين تصف توريث الدور والتخصيص الفردي: [خطة صلاحيات المستخدمين](./user-permissions-plan.md).
- توجد اختبارات ذات صلة بالصلاحيات ونطاق الفروع والأدوار والمشتريات والمبيعات، ومنها `tests/access-governance.php` و`tests/branch-scope.php` و`tests/role-management.php` و`tests/user-permissions.php` و`tests/purchasing-scenarios.php` و`tests/sales-journey-http.php`.

هذه مؤشرات أولية فقط، ولا تثبت اكتمال التغطية أو صحة كل حارس وصول. يجب حصر جميع الملفات والاستخدامات والاختبارات في المرحلة الأولى. كما يجب تسوية أي تعارض بين هذه الخطة ووثيقة صلاحيات المستخدمين القائمة قبل التنفيذ، وعدم كسر سلوك التوريث أو الاستثناءات الفردية.

## 3. الأهداف ومؤشرات الاكتمال

### الأهداف

1. توحيد أسماء القدرات ومعناها ومكان تعريفها، مع تجنب نسخ فحوص الصلاحية المتباينة بين الملفات.
2. فصل صلاحية الفعل عن نطاق المورد: امتلاك قدرة لا يثبت تلقائيًا حق الوصول إلى كل سجل أو فرع.
3. حماية العمليات داخل الخدمات، وكذلك نقاط REST، وعدم اعتبار إخفاء الأزرار حماية.
4. تقليل الصلاحيات الواسعة، وتطبيق أقل صلاحية وفصل الواجبات في العمليات الحساسة.
5. منع IDOR وتسرب البيانات بين المستخدمين والفروع، بما في ذلك القوائم والتقارير والتصدير.
6. تسجيل العمليات الحساسة بالاستفادة من سجل التدقيق القائم بدل إضافة سجل موازٍ دون ضرورة.
7. تنفيذ التغيير تدريجيًا، مع ترحيلات متكررة بأمان، وخطة تراجع، واختبارات التوافق الحالية.

### مؤشرات قبول قابلة للتحقق

- لكل عملية تجارية حساسة: قدرة موثقة، وحدود نطاق معلومة، وحارس خدمة، وحماية API عند وجود نقطة API، واختبار سماح واختبار منع.
- لكل شركة عميلة: ملف قرار/تهيئة مستقل لموقعها يحدد النطاق والأدوار والأغراض والحقول والاستثناءات؛ ولا تُورّث قرارات عميل إلى آخر.
- إذا طلب عميل تشغيل شركات مستقلة في تثبيت/قاعدة مشتركة، فيلزم معرف مؤسسة موثوق من الخادم وعزل مؤسسي شامل للقراءات والكتابات والتقارير والتصدير والملفات والمهام الخلفية، واختبارات منع بين مؤسستين قبل اعتبار ذلك نمط نشر مدعومًا. لا تكفي حدود الفروع الحالية لإثباته؛ ولا يُفترض هذا النمط للاستخدام المعتاد للمنتج.
- لا يمكن الوصول إلى مورد خارج ملكية المستخدم أو نطاقه بمجرد تغيير معرّف الطلب.
- استعلامات القوائم والتقارير لا تجلب أو تكشف سجلات خارج النطاق المصرح.
- لا يمنح `manage_options` صلاحية تجارية ضمنية؛ تبقى استخداماته الإدارية النظامية فقط.
- نتائج ترحيل الصلاحيات موثقة، متكررة بأمان، ولا تمحو تخصيصات أو أدوارًا أو منحًا مباشرة غير مملوكة للترحيل.
- جميع الاختبارات السابقة ذات الصلة تظل ناجحة، مع اختبارات تفويض جديدة موثقة.

## 4. ما يدخل في النطاق وما لا يدخل فيه

### داخل النطاق

- حصر الأدوار والقدرات ومنح الأدوار والمستخدمين المباشرة والتخصيصات.
- CRM والعملاء والمهام التسويقية، المبيعات والحجوزات والخصومات، التسعير، المالية والمدفوعات والمبالغ المستردة.
- المخزون وVIN والنقل والتعديلات، المشتريات والاستلام والاعتماد، التسليم والإرجاع.
- خدمة العملاء، التقارير، التدقيق، التكاملات، الصندوق الصادر، وإدارة محتوى/كتالوج الموقع حيث تنطبق صلاحيات العمل.
- حماية الخدمة وREST وواجهات الإدارة والصفحات والنماذج والاستعلامات والاستجابات.
- الترحيل، الاختبارات، التوثيق والتشغيل المرحلي.

### خارج النطاق ما لم يثبت التدقيق ضرورة ذلك

- إعادة كتابة بنية الإضافة أو استبدال WordPress Roles/Capabilities.
- تغييرات مخطط قاعدة البيانات أو إضافة بيانات وصفية للفروع/المالكين دون إثبات الحاجة. **لكن إذا طلب عميل تشغيل عدة شركات في تثبيت/قاعدة مشتركة، يصبح إثبات حد عزل موثوق بينها شرطًا معماريًا منفصلًا يسبق النشر، وليس تحسينًا اختياريًا لهذه المرحلة.**
- تغيير أسماء المسارات أو صيغة الاستجابات العامة، أو تغيير دورة العمل التجارية.
- إعادة تصميم واجهات الإدارة أو استحداث إطار اختبارات جديد.
- إعادة تعريف سياسات الخصم أو الاعتماد المالي بأرقام غير موثقة من العمل الحالي.

أي تغيير مستثنى لا يُضاف إلا بعد توثيق الحاجة، والبدائل، والأثر، والموافقة.

### شرط مشاركة التثبيت بين شركات مستقلة

ملف القرار المستقل لكل شركة عميلة هو فصل حوكمي ولا ينشئ عزلًا تقنيًا. في نمط الاستخدام المعتاد، يكون لكل شركة تثبيت وموقع وقاعدة منفصلة، ويوثق ذلك في ملفها. أما إذا طلب عميل أن تشترك شركات مستقلة في تثبيت/قاعدة، فلا يبدأ هذا النشر قبل مشروع معماري يثبت، على الأقل:

1. معرف المؤسسة مملوكًا لمصدر هوية/تثبيت موثوق ويُشتق من سياق المصادقة على الخادم، لا من الطلب أو اختيار الواجهة.
2. تغطية العزل لكل قراءة وكتابة واستعلام بحث/تصدير، REST وAJAX والإدارة والملفات المباشرة، والمهام الخلفية والتكاملات وسجلات التدقيق.
3. منع وصول مسؤول مؤسسة إلى بيانات مؤسسة أخرى، مع توثيق استثناءات دعم المنتج/المشغل بمسار منفصل ومحدود ومدقق.
4. اختبارات HTTP/الخدمة لشركات اختبار اصطناعية منفصلة، تشمل تبديل معرف الشركة، المعرفات المفقودة، المهام المؤجلة، الروابط المباشرة، والتقارير والتصدير.
5. ترحيلًا وخطة استعادة وإثباتًا لعدم خلط البيانات الحالية؛ لا يُستخدم اختبار على قاعدة الإنتاج لإثبات الفصل.

إلى حين اجتياز هذه البوابة، يكون تثبيت مستقل لكل شركة هو الافتراض الآمن، ويظل تشغيل شركات مستقلة في تثبيت/قاعدة مشتركة «غير مدعوم/غير مثبت» لا مجرد إعداد سياسة.

### حالة التنفيذ الفني للمراحل 3–8 — 2026-10-23

هذا تحديث حالة لا يعد اعتمادًا لسياسة عميل أو تصريحًا بإطلاق إنتاجي:

- **المرحلتان 3–4:** توجد آليات التفويض والنطاق الحالية واختبارات ترحيل وقراءات REST/HTTP موثقة في تقرير التدقيق. نجحت مجموعة السيناريوهات المعزولة في **973 تحققًا** في التشغيل الأخير. تظل التغطية جزئية ولا تثبت اختبار كل تبديلات الدور/الملكية/الفرع أو كل مخرج وواجهة؛ لا تُعلن بوابتا المرحلتين مغلقتين حتى استكمال المصفوفة المعتمدة.
- **المرحلتان 5–6:** حافظ هذا التغيير على صلاحيات الأدوار وسلوكها، وأضاف تسجيلًا تدقيقيًا لتصدير CRM. لا يمكن إتمام شرائح المجال أو إعلان تكافؤ كل الواجهات قبل إغلاق المرحلة 2 واعتماد P-01–P-08 للعميل المعني؛ لا تُستنتج سياسة الخصم أو التصدير أو الوصول من صلاحيات المصدر وحدها.
- **المرحلة 7:** يسجل تصدير CRM الفاعل وعدد الصفوف فقط قبل إرسال CSV، ولا يرسل الملف إذا فشل التسجيل. التحقق HTTP المعزول يغطي النطاق، وتحييد الصيغ، ومحتوى الحدث المختصر، ومسار الفشل. يظل نطاق وصول Auditor وتنقيح سجل التدقيق ومدة الاحتفاظ قراراتًا مفتوحة في P-06.
- **المرحلة 8:** لم تُزل قدرات أو حراس قديمة ولم يُنفذ إطلاق أو ترحيل على قاعدة الموقع؛ لم يثبت عدم استخدام المراجع القديمة ولم تصدر موافقات الإطلاق اللازمة. لا تبدأ هذه المرحلة قبل قرارات العميل المخول، ونتائج مصفوفة الاختبارات النهائية، ومراجعة خطة التراجع والإطلاق.

## 5. مبادئ التصميم الأمني

1. **الرفض الافتراضي:** كل فعل غير موثق أو مورد لا يمكن إثبات نطاقه مرفوض.
2. **القدرات دقيقة ودلالية:** القدرة تمثل فعلًا محددًا، ولا تُستخدم أدوار المستخدمين كبديل عن التفويض.
3. **القدرة لا تكفي وحدها:** يضاف فحص الملكية، والفرع، والحالة، ونوع المورد، وقاعدة العمل عند الحاجة.
4. **هوية الخادم هي المرجع:** لا تُقبل `user_id` أو `branch_id` أو الدور أو المالك من الطلب لتقرير الصلاحية.
5. **الخدمة هي مرجع القرار التجاري:** كل عملية كتابة أو اعتماد حساسة محمية عند مدخل الخدمة، حتى إن كان لها `permission_callback`.
6. **API محمي مستقلًا:** لكل REST route حساس `permission_callback` صريح، مع إبقاء فحص الخدمة.
7. **تصفية مبكرة للبيانات:** القيود تطبق في الاستعلام أو طبقة الوصول قبل إخراج الموارد، لا بعد إرسال البيانات إلى الواجهة.
8. **فصل الواجبات:** لا يجمع المستخدم صلاحيات إنشاء العملية والتحقق/اعتمادها عندما تتطلب السياسة فصلًا.
9. **التوافق أولًا:** لا تزال صلاحيات WordPress، والأدوار المخصصة، والمنح/المنع الفردية، وتخصيصات الدور قائمة ما لم يعتمد تغيير محدد.
10. **لا قوائم منع بديلة عن التفويض:** يمكن استخدام المحظورات كاختبارات ثوابت، لكن قرار السماح يبنى على الصلاحية الإيجابية والنطاق.
11. **لا تجاوز تجاري عام:** تظل `manage_options` للصيانة والإعدادات الإدارية المبررة فقط.
12. **أثر قابل للتتبع:** كل قرار أو ترحيل أو عملية حساسة له دليل اختبار أو سجل مناسب.

| CRM / العملاء المحتملون | إنشاء، عرض، تعديل بيانات الهوية، إضافة نشاط، تحديث المرحلة، إعادة إسناد، حذف، عرض قياسات الحملة |
| المبيعات والحجوزات | إنشاء/تحرير عرض سعر، طلب خصم، مراجعة/اعتماد خصم، إنشاء/إدارة حجز، اعتماد بيع، إلغاء بيع |
| التسعير | عرض السعر/التكلفة، طلب تغيير السعر، إدارة التسعير، اعتماد خصم ضمن حدود معتمدة |
| المالية | عرض المالية، تسجيل دفعة، التحقق من دفعة، تسجيل/التحقق من استرداد، عرض مستند مالي |
| المخزون | عرض/إدارة المخزون، تأكيد VIN، نقل مركبة، تسوية أو تعديل مخزون |
| المشتريات | عرض/إنشاء/تحرير أمر شراء، استلام، اعتماد، إلغاء |
| التسليم | عرض قائمة التسليم، تأكيد VIN/التسليم، معالجة الإرجاع |
| خدمة العملاء | عرض ضمن النطاق، إضافة تفاعل، إنشاء حجز وفق السياسة |
| التقارير والتدقيق | عرض تقارير محددة، مؤشرات مجال محدد، سجل التدقيق، التكاملات، الصندوق الصادر |
| المحتوى والكتالوج | الحفاظ على قدرات WordPress الحالية وفصلها عن صلاحيات العمليات التجارية |

يجب اختيار مفردات موحدة للأفعال وتحديد معنى كل قدرة، والموارد التي تغطيها، وما إذا كانت قراءة أو كتابة أو اعتمادًا. لا تنشأ قدرة عامة مثل `manage_*` إذا أمكن تحديد عمليات مستقلة دون تعقيد غير مبرر.

### 6.2 النطاقات المرشحة

- **own:** موارد يملكها المستخدم وفق حقل موثوق في قاعدة البيانات.
- **created_by_me:** موارد أنشأها المستخدم؛ لا تساوي تلقائيًا موارد مسندة إليه.
- **assigned_to_me:** موارد مسندة إليه حاليًا.
- **branch:** موارد فرع المستخدم/الفروع المصرح بها.
- **region:** موارد المنطقة المخولة عند وجود نموذج مناطق فعلي.
- **organization:** نطاق المؤسسة عند وجود سياسة ودور يجيزان ذلك.
- **reporting_only:** بيانات مجمعة/محدودة للقراءة دون صلاحيات تشغيلية.

لا يفترض وجود كل هذه الأبعاد في قاعدة البيانات. المرحلة الأولى تحدد الحقول الفعلية والعلاقات ومصدرها الموثوق. عند غياب معلومة لازمة لإثبات النطاق، يكون القرار رفضًا واضحًا أو حجبًا للبيانات، لا توسيعًا تلقائيًا.

### 6.3 قرار التفويض

ينبغي توفير نقطة تفويض مشتركة أو توحيد المساعد الحالي، بحسب ما يكشفه التدقيق. واجهة مفاهيمية ممكنة:

```php
Authorization::can(
    'adc_view_marketing_leads',
    array(
        'resource_type' => 'lead',
        'resource_id'   => $lead_id,
        'action'        => 'view',
    )
);
```

هذه واجهة توضيحية فقط، وليست قرارًا بإنشاء صنف أو توقيع جديد. يجب أن تقبل الطبقة سياقًا موثوقًا أو تحمّل المورد بنفسها؛ ولا تعتمد على `branch_id` أو `owner_id` قادم من العميل. ينبغي أن تفصل نتيجة القرار بين: هوية صالحة، قدرة الفعل، نطاق المورد، حالة المورد، وقاعدة العمل، مع رسالة/خطأ متوافق مع أنماط الإضافة الحالية.

## 7. مصفوفة الأدوار الأولية

هذه مصفوفة سياسة مبدئية للنقاش، وليست تفويضًا لتغيير الأدوار. تعتمد الحقوق الدقيقة على التدقيق، سياسات المؤسسة، ومصفوفة `Capabilities` الحالية. كل علامة سماح تظل مقيدة بنطاق المورد والفرع والحدود المعتمدة.

| الدور | المهام المسموحة مبدئيًا | قيود إلزامية |
|---|---|---|
| Marketing | إنشاء وعرض العملاء التسويقيين، تعديل الهوية المحددة، إضافة نشاط تسويقي، مؤشرات الحملات | لا تغيير للمراحل التجارية أو الأسعار أو الخصومات أو المالية أو المخزون؛ لا حذف أو نقل نطاق دون تفويض |
| Sales | إدارة العملاء المسندين، عروض الأسعار، طلب الخصم، الحجوزات والأنشطة البيعية المسموحة | لا اعتماد ذاتي لخصم/عملية تتطلب فصلًا؛ لا إدارة مالية أو مخزون؛ لا وصول لفروع أخرى |
| Sales Manager | نطاق الفرع، إدارة/إسناد العملاء، مراجعة الخصومات والاعتمادات المحددة | لا صلاحية مالية أو تكلفة مركبة أو إدارة مخزون شاملة افتراضيًا |
| General Manager | صلاحيات تشغيلية صريحة حسب مسؤولياته، واعتمادات أعلى بعد توثيق السياسة | لا تجاوز شامل عبر `manage_options`؛ لا يكتسب أي قدرة لمجرد المسمى الوظيفي |
| Finance | العمليات المالية المحددة: عرض، تسجيل، تحقق، استرداد، مستندات | فصل التسجيل عن التحقق حيث تدعم السياسة؛ لا تعديل للمبيعات أو المخزون أو التسعير دون قدرة مستقلة |
| Inventory | عرض وإدارة المخزون، النقل، VIN، التسويات المعتمدة | لا مالية ولا اعتماد مبيعات أو خصم أو إسناد عملاء |
| Purchasing | إنشاء/تحرير/استلام أوامر الشراء حسب الفصل المعتمد | لا تنفيذ واعتماد الدورة كاملة لمستخدم واحد إذا كانت السياسة تتطلب فصلها |
| Delivery | قائمة التسليم، تأكيد التسليم/VIN، الإرجاع وفق الخدمة الحالية | لا إدارة مخزون كاملة أو مالية أو تسعير أو اعتماد مبيعات |
| Customer Service | تفاعل العميل والموارد المصرح بها ضمن النطاق، وحجز وفق السياسة | لا مالية أو تسعير أو اعتماد مبيعات أو تعديل مخزون |
| Auditor | تقارير وسجلات للقراءة فقط بالحد اللازم | منع جميع عمليات الكتابة والتشغيل؛ عدم كشف حقول مالية خارج نطاق التدقيق |
| أدوار WordPress/المخصصة الأخرى | تُحصر وتُصنف قبل التصرف فيها | لا حذف ولا تغيير تلقائي؛ تبقى صلاحيات المحتوى وإدارة WordPress منفصلة |

### ضوابط خاصة

- **Marketing:** تُراجع دورة العميل الحالية قبل اعتماد أي انتقال حالة. التسلسل المقترح (إنشاء → إسناد → تواصل → تأهيل → حجز → بيع/إغلاق) لا يستبدل دورة العمل المنفذة حتى يثبت التطابق.
- **الإسناد:** القدرة المقترحة `adc_assign_marketing_leads` ليست افتراضية لكل مسوق؛ تُمنح لمن يقرره نموذج الفرع. كل تغيير إسناد يوثق.
- **المدير العام:** تمنح قدرات تشغيلية محددة، لا تجاوزًا عامًا.
- **المدقق:** قراءة فقط فعليًا على الخدمة وAPI والواجهة والاستعلامات، وليس مجرد غياب أزرار الكتابة.
- **الحدود المالية:** لا تثبت نسب مثل 5% أو 10% إلا إذا وجدت سياسة حالية موثقة. إن لم توجد، توضع كقرار أعمال منفصل قبل بناء آلية قابلة للضبط.

## 8. مراحل التنفيذ وبوابات الاعتماد

تُنفذ المراحل بالتسلسل. لا ينتقل الفريق من مرحلة إلى التالية قبل استيفاء مخرجها ومعيار خروجها، وتوثيق حالات الإخفاق والقرارات المفتوحة.

### المرحلة 0 — التحضير وحدود التغيير

**الهدف:** تثبيت خط أساس آمن وتحديد بيئة التنفيذ.

**الأعمال:**

- تحديد الفرع البرمجي والبيئة والنسخة/إصدار المخطط وأدوات الاختبار الحالية.
- توثيق نموذج تقديم المنتج لدى كل عميل: المعتاد تثبيت مستقل للقالب والإضافة على موقع الشركة؛ أما WordPress Multisite أو تثبيت/قاعدة مشتركة لعدة شركات فهو خيار استثنائي يحتاج تحديدًا صريحًا وتقييمًا مستقلًا، ولا يُفترض من مجرد كون المنتج يباع لشركات مختلفة.
- عند طلب تثبيت مشترك، جرد حدود المؤسسة لكل الجداول والعلاقات والملفات والتخزين المؤقت والمهام المجدولة والتكاملات وسجلات التدقيق؛ وتحديد مصدر سياق المؤسسة الموثوق على الخادم. لا يقبل معرف المؤسسة من مدخل العميل كمرجع للتفويض.
- جرد حالة Git والاختبارات المتاحة دون إدخال تغييرات غير مرتبطة.
- تحديد مسارات العمل الحرجة التي يجب ألا تتوقف: تسجيل العملاء، البيع والحجوزات، المالية، المخزون، المشتريات والتسليم.
- تأكيد عدم استخدام بيانات إنتاج حساسة في الاختبارات، وتحديد بيئة اختبار معزولة.

**المخرجات:** خط أساس للنسخة والاختبارات، قائمة مسارات حرجة، وخطة حفظ/استعادة بيانات الترحيل، وقرار موثق لنمط نشر كل عميل.

**بوابة الخروج:** يمكن تشغيل الاختبارات الحالية ذات الصلة أو توثيق سبب تعذرها وخطة بديلة قبل بدء التغيير. تثبيت العميل المستقل هو النمط المباشر الذي تصفه الخطة. لا يُعتمد تثبيت مشترك لعدة شركات إلا بعد تحديد أنه مطلوب فعلًا وتوفير خريطة حد العزل وخطة هندسية واختبارات سلبية عبر مؤسستين اصطناعيتين على الأقل.

### المرحلة 1 — التدقيق الشامل (قراءة فقط)

**الهدف:** وصف الواقع كما هو دون تعديل أي ملف أو سجل أو إعداد.

**الأعمال:**

1. حصر الأدوار الافتراضية والمخصصة، قدراتها، منح المستخدم المباشرة، حالات المنع/التخصيص الفردي، والأدوار المحمية.
2. حصر تعريف القدرات ومهاجرات الأدوار وإصداراتها ومصادر تشغيلها في دورة حياة الإضافة.
3. البحث عن `current_user_can` و`user_can` و`add_cap` و`remove_cap` و`get_role` وخرائط القدرات، مع سياق كل استخدام.
4. حصر REST routes و`permission_callback` وعمليات `admin-post` وAJAX والنماذج والمسارات العامة ذات الصلة.
5. تتبع كل عملية حساسة من الواجهة إلى API/المعالج والخدمة والاستعلام ومخزن البيانات.
6. حصر فحوص الخدمات، وفحوص الوصول للصفحات والقوائم، ومصادر بيانات القوائم والتقارير والتصدير.
7. تحليل نطاق الفروع والملكية والإسناد لكل نوع مورد، ومصدر `branch_id` الفعلي.
8. جرد الحقول الحساسة التي تخرج في الاستجابات/التقارير، وحواجز `manage_options` والصلاحيات الواسعة.
9. جرد اختبارات الأدوار والنطاق وHTTP وIDOR والتوافق؛ تحديد ما تثبته وما لا تغطيه.
10. إنشاء مصفوفة فجوات ومخطط تبعيات، دون كتابة إصلاحات ضمن هذه المرحلة.

**المخرجات الإلزامية:**

- سجل الأدوار والقدرات والمنح/الاستثناءات الفعلية.
- فهرس المسارات والخدمات والواجهات وفحوص التفويض.
- مخطط تدفق لكل عملية حساسة من مدخل الطلب حتى البيانات.
- قائمة فجوات مرتبة حسب الشدة والاحتمال والأثر.
- حالات IDOR، العزل بين الفروع، تسريب البيانات، ضعف `permission_callback` أو تفويض الخدمة، مع أدلة ملف/موضع.
- خريطة الاختبارات الحالية والاختبارات الناقصة.
- توصيات ترحيل وتراجع مرتبطة بكل فجوة، دون تنفيذها.

**بوابة الخروج:** مراجعة بشرية للتدقيق، حسم التعارضات مع الوثائق/الاختبارات القائمة، واعتماد نطاق المرحلة التالية. إذا كانت النتائج غير مكتملة، تستكمل هذه المرحلة فقط.

### المرحلة 2 — اعتماد نموذج التفويض ومصفوفة الأدوار

**الهدف:** تحويل نتائج التدقيق إلى سياسة دقيقة قابلة للاختبار.

**الأعمال:**

- تثبيت معجم القدرات وربط كل قدرة بالفعل والمورد وطبيعة القراءة/الكتابة/الاعتماد.
- اعتماد الأدوار الفعلية، بما فيها الأدوار المخصصة، دون إسقاط الأدوار غير الواردة في المقترح.
- توثيق Scope ومصدر كل حقيقة: المستخدم الحالي، الفرع/الفروع، المالك، المسند إليه، حالة المورد.
- توثيق حقول البيانات الحساسة وما يمكن لكل مجال رؤيته.
- توثيق انتقالات الحالات، حدود الخصم/الشراء/الاسترداد الموجودة، ومسؤولية الاعتماد.
- توثيق قدرات WordPress التي يجب أن تبقى إدارية أو خاصة بالمحتوى.
- مقارنة المصفوفة بخطة [صلاحيات المستخدمين الحالية](./user-permissions-plan.md) وتحديد التغييرات أو التوافق المطلوب.
- فصل مصفوفة المنتج المشتركة عن ملفات العملاء: تحدد الأولى معاني القدرات والضوابط التقنية الافتراضية؛ ويسجل لكل عميل على حدة ما يختاره لموقعه من أدوار وأغراض وحدود وحقول واستثناءات واحتفاظ. لا تُدمج قرارات العملاء في baseline عام ولا يُفترض تطابقها.
- تسجيل نمط نشر موقع كل عميل؛ لا يُعامل WordPress Multisite أو قاعدة مشتركة لعدة شركات كجزء من نمط المنتج المدقق إلا إذا طلبه العميل واجتاز شرط العزل في المرحلة 0.

**المخرجات:** قاموس قدرات مشترك للمنتج، ومصفوفة baseline غير نافذة، وقالب ملف قرار/تهيئة مستقل لكل عميل، ومخطط تدفق موافقات لكل نطاق، وسجل مخاطر يميز بين مخاطر المنتج وخيارات العملاء، وقائمة تغييرات مرشحة لكل مرحلة.

**بوابة الخروج:** اعتماد مالك المنتج لخصائص baseline المشتركة، واعتماد ممثلي كل عميل مخولين لملف موقعه بشأن الصلاحيات الحساسة والحدود المالية وسلوك الأدوار المخصصة. إذا لم يُعيّن ممثلو العميل، يبقى ملف موقعه بانتظار التعيين؛ ولا تُخمن السياسة التجارية ولا تعمم موافقة عميل على آخر.

**التنفيذ الجاري:** أُنجز جرد أولي من المصدر والاختبارات، وأُعدت مسودة قاموس ربط ومصفوفة baseline قابلة للمراجعة تفصل الوقائع عن السياسة المقترحة. أُضيف قالب ملف قرار/تهيئة مستقل لكل عميل يفصل قرارات موقعه عن baseline المنتج. لا تُعد هذه المخرجات اعتمادًا ولا تغيّر الصلاحيات. يستمر العمل بربط كل قدرة بمساراتها وحقولها ونطاقها؛ وتظل فروق الأدوار التجارية والحدود المالية وفصل الواجبات محجوبة حتى اعتمادها من أصحاب الصلاحية لدى العميل المعني. لا تُغلق المرحلة 2 ولا تبدأ المرحلة 3 للتغييرات الخاصة بموقع عميل قبل اكتمال مخرجاته وتسجيل موافقاته؛ وأي طلب لتثبيت مشترك يتطلب اجتياز بوابة العزل المعماري.

#### 2.1 خط أساس الأدوار من المصدر (للمراجعة، غير معتمد)

**حدود ما يثبته خط الأساس:** القوالب ليست الحالة الفعلية النهائية دائمًا. تعريف `adc_role_definitions` قد يغير مجموعة القدرات التي يستهدفها مدير الأدوار، لكن تفعيل الأدوار إضافةٌ للقدرات المستهدفة ويحافظ على المنع الصريح المسجل؛ لذلك قد تبقى قدرات موجودة مسبقًا في الدور. التخصيص الفردي يحفظ سماحًا/منعًا صريحًا لكل قدرة قابلة للتعيين، والمنح المؤقتة تتجاوز المنع الفردي حتى انتهاء صلاحيتها، والتعليق يحجب الوصول للمستخدم غير المحمي. المسؤول محمي وتزامن الإضافة قدرات العمل له؛ كما أن صلاحيات WordPress الأصلية قد توسع صلاحيات المحتوى. الترحيلات الإصدارية قد تضيف منحًا في الأدوار/المستخدمين وفق قواعدها. لذلك يلزم تقرير effective access لكل حساب قبل اعتماد المصفوفة التشغيلية؛ لم يُفحص اتصال قاعدة بيانات الموقع أو بيانات مستخدميه في هذا العمل.

#### 2.1.1 دورة بناء القدرات ومصادر الانحراف عن القالب

#### 2.3.1 ربط القدرة بالفعل وحدود التفويض المتحققة في المصدر

هذا جرد تقني لما أمكن تثبيته من الخدمات المحورية، وليس حكمًا بأن القيود الحالية هي السياسة المعتمدة. «غير محسوم» يعني أن الفحص الحالي لم يثبت بعد جميع المستهلكين والحقول أو أن معنى القدرة يحتاج قرارًا؛ لا يعني تلقائيًا وجود ثغرة.

| القدرات | الفعل/البيانات | شرط المورد أو القيد المثبت في المصدر | نتيجة المرحلة 2 |
|---|---|---|---|
| `adc_view_workspace` | دخول مساحة العمل ولوحة الملخص | يفتح واجهة/ملخصًا؛ لا يكفي وحده لتنفيذ إجراء CRM أو مالي أو مخزني، وبعض الوحدات تتطلب قدرة مجال إضافية. | يؤكد الفصل بين دخول الواجهة وتفويض العملية. يلزم فحص التقارير/المربعات التي يجمعها الملخص وما إذا كانت كل استعلاماته محدودة بحسب قدرات المجال. |

#### 2.3.2 جرد واجهة REST ومسارات التفويض

يسجل `Routes::route()` المسارات في namespace التوافق `auto-dealership/v1` وفي `auto-dealership/v2` مع عقد الاستجابة المغلف لـv2. يلخص الجدول المسارات الوظيفية من تعريفات Routes؛ لا يكرر المسار مرة لكل namespace. يجب استمرار التحقق من الحارس في الخدمة والنطاق على المورد، خصوصًا عندما يكون `permission_callback` شرط قدرة عامًّا أو يكتفي بتسجيل الدخول.

#### 2.3.5 جرد حقول المخطط ومراجعة الوصول الفعلي — لقطة تاريخية

أُجري في 2026-10-23 استعلام قراءة فقط على قاعدة WordPress `wp-autobrands`، دون قراءة أسماء المستخدمين أو البريد أو كلمات المرور أو محتوى سجلات العملاء، ودون أي كتابة. أكد المستخدم لاحقًا أن هذه القاعدة تخص موقعًا محليًا يعدّه إنتاجًا؛ لذا تُقرأ نتائج هذا القسم كلقطة تاريخية لحالة إنتاجية وليست قاعدة تطوير. شمل فحص المخطط 53 جدولًا للإضافة و3 جداول `car-dealer`، وحُصرت 202 خانة مرشحة لمراجعة الخصوصية في 51 جدولًا `wp_adc_*` بحسب أسماء الحقول وأنواعها. هذا **جرد لمواضع التخزين المحتملة، لا إثبات بأن كل خانة تُعرض للمستخدم**؛ ربط كل استجابة/تقرير/تصدير بهذه الخانات واختبارات الرفض الفردية يظل عملًا مطلوبًا.

**لقطة تاريخية بعد إنشاء بيانات المراجعة:** وثقت قاعدة `wp-autobrands` 23 حسابًا: المسؤول و22 حساب مراجعة بعلامة `adc_rbac_review_fixture`. كان التوزيع حسابًا لكل دور من `Capabilities::role_matrix()` في الفرع 1، مع حساب إضافي في الفرع 2 لكل دور تشغيلي من الأدوار العشرة؛ حساب العميل وAuditor بلا فرع. تحقق قراءة القاعدة آنذاك أن حسابات المراجعة تحمل دورًا واحدًا لكل حساب، بلا قدرات مباشرة مضافة في سجل دور المستخدم؛ واختبارات runner المعزولة تطابق قدرات الأدوار الـ12 مع baseline وترفض `manage_options` عنها. كلمات المرور عشوائية لم تُحفظ أو تُعرض، والبريد على `example.invalid`. أكد المستخدم لاحقًا أن القاعدة إنتاج؛ لا تعتبر هذه اللقطة التاريخية وصفًا راهنًا ولا بيانات هذه الحسابات بيانات موظفين.

وثقت اللقطة التاريخية عميلين وفرصتين اصطناعيتين، واحدة لكل فرع، وموافقة تسويق false؛ كل فرصة كانت مسندة إلى حساب المبيعات الاصطناعي في فرعها. وثقت كذلك 4 سجلات نشاط و133 حدث تدقيق. هذه بيانات مراجعة اصطناعية موجودة في قاعدة الإنتاج وفق تأكيد المستخدم، ولا تمثل سجلات عملاء حقيقيين أو موافقة سياسة. لا تُفعّل الحسابات تشغيليًا ولا توزع بيانات اعتماد ولا تحذف هذه السجلات قبل قرار مالك النظام. أعاد `wp_get_environment_type()` قيمة `production`، وهو متسق مع تصنيف المستخدم للموقع.

#### دليل الفحوص وحالة التغطية السلوكية

تم التحقق على الموقع المحلي الذي أكد المستخدم أنه إنتاج (PHP 8.2.12، WordPress 7.1.3، MariaDB 10.4.32، مخطط الإضافة `1.29.0`، أدوار `1.65.2`). اجتازت اختبارات `branch-scope.php` **52 تحققًا** واختبارات `response-contract.php` **9 تحققات** دون اتصال قاعدة. نجح أحدث تشغيل لـ`ADC_DATABASE_SCENARIOS_ONLY=1` على قاعدة اختبار منفصلة بإجمالي **973 تحققًا**، منها اختبارات HTTP لتصدير CRM تثبت تحييد خلايا الصيغ، وقصر CSV على فرصة المالك واستبعاد فرصة زميله وفرصة الفرع الآخر، ورفض الدور غير المخول، وتسجيل الفاعل وعدد الصفوف دون معلومات شخصية، ومنع الملف عند فشل التسجيل؛ أزيلت قاعدة الاختبار ولم تُستخدم بيانات الموقع في سيناريوهات الكتابة. هذه نتائج اختبار معزول لا اختبار كتابة على بيانات الإنتاج. لا تُعد أرقام الاختبارات المعزولة إثباتًا لسياسة تصدير معتمدة أو لوصول المستخدمين الفعلي إلى سجلات الإنتاج.

**نطاق موثق في التنفيذ الحالي:** `BranchScope` يستمد الفروع من `adc_branch_id` و`adc_branch_ids` المخزنين للمستخدم، ولا يمنح تعيين الفرع أي قدرة فعلية. الفروع غير النشطة لا تجتاز `allows()`؛ والمسؤول ذو `manage_options` نطاقه شامل. لا توجد أبعاد Region أو Organization مستقلة مثبتة في نموذج `BranchScope` الحالي، فلا تُضاف إلى السياسة دون مصدر بيانات وقرار معتمد.

#### 2.5.1 سجل توقيع واعتماد السياسة والخصوصية — مسودة غير معتمدة

أُعد هذا السجل لتسهيل المراجعة الرسمية. **لا يمثّل توقيعًا أو موافقة أو تفويضًا قائمًا**، ولا يتغير أي منح/رفض أو مخرج بيانات قبل اكتمال حقول الاعتماد والتحقق من صفة صاحب القرار. يسجل المراجع قرارًا واحدًا محددًا لكل نطاق، لا عبارة عامة من نوع «موافق على المرحلة».

يتوفر [سجل مستقل لمسودات القرارات والتوقيع](./AUTHORIZATION-POLICY-PRIVACY-SIGNOFF-AR.md)، ويحتوي مسودات تفصيلية لـP-01 إلى P-08 تشمل الحالة الفنية والنطاق والحقول والضوابط ومعايير القبول والجهات الموقعة ونموذج إثبات القرار. المسودات غير نافذة؛ جميع البنود بانتظار اعتماد أصحاب الصلاحية.

**قواعد قبول السجل:** يرفق لكل قرار مالك محدد مخول بالتوقيع، والقرار والسبب والغرض ونطاق المستخدم/الفرع والحقول المتأثرة والمدة/الاحتفاظ عند انطباقها، وتاريخ النفاذ ومرجع الإثبات. لا يكفي إقرار مطور أو إنشاء الحسابات الاصطناعية بدل اعتماد مالك البيانات. عند عدم استيفاء أي خانة تظل الحالة «بانتظار الاعتماد» وتظل المرحلة مفتوحة.

**قرار الجاهزية:** اكتمل تعداد baseline المصدر للقدرات ومسارات REST وhooks، وربط القدرات الـ59 في كتالوج الإضافة بفعل/مجال، وجرد حقول مخطط التخزين، وإنشاء حسابات مراجعة اصطناعية لأدوار المصفوفة مع عينة فرع ثانٍ. أكد المستخدم أن قاعدة الموقع إنتاج؛ هذه الحسابات والبيانات الاصطناعية موجودة فيها، لكنها لا تمثل موظفين أو عملاء حقيقيين ولا اعتمادًا. ما زالت قرارات السياسة المطلوبة تشمل وصول المنشئ التسويقي عبر الفروع، وتصدير PII، وأداء الموظفين، ونطاق Auditor وحقول سجل التدقيق، والقدرة التي لا يظهر لها مستهلك مباشر. حساب العميل وAuditor بلا إسناد فرع، ولا يكتمل تتبع كل حقل لكل استجابة/واجهة/تصدير أو اختبارات الرفض الشاملة. لم تُسجل موافقات أصحاب السياسة والخصوصية. لذلك المرحلة 2 **قيد التنفيذ ومفتوحة**؛ لا تُفعّل حسابات المراجعة تشغيليًا ولا تغيّر الصلاحيات قبل الاعتماد.

### متابعة تنفيذ — متانة ترحيلات الصلاحيات

- عولجت مخاطرة إكمال الترحيل بعد فشل جزئي دون تغيير أي منح مقصود: ترحيلات التسويق والنشرة والمشتريات والمبيعات تتحقق الآن من التخزين الفعلي للقدرات وتعريفات الأدوار ومِنح المستخدمين وعلامات الإصدارات، وتسجل فشلًا صريحًا وتترك الترحيل قابلًا للاستئناف.
- اختبارات fault injection أثبتت أن فشل كتابة دور أو اكتشاف المستخدمين أو حفظ منحة مباشرة أو كتابة علامة الإصدار لا يسجل نجاحًا كاذبًا، وأن إعادة المحاولة تُكمل التغييرات الإضافية بأمان.
- التحقق: `ADC_DATABASE_SCENARIOS_ONLY=1` نجح بـ **836 تحققًا** على قاعدة مؤقتة؛ `ADC_CATALOG_ONLY=1` نجح بـ **388 تحققًا** على قاعدة مؤقتة؛ وفحوص PHP و`git diff --check` ناجحة. التشغيل المجمع الكامل تعثر بعد 831 تحققًا عند إنشاء fixture فرع داخل `catalog-publishing-scenarios.php`، بينما اجتازت مجموعة الكتالوج المنفصلة جميع اختباراتها. أُزيلت قواعد الاختبار، ولم تُستخدم قاعدة الموقع.
- الحدود: الترحيلات ليست معاملة ذرية عبر جداول WordPress المتعددة؛ هي additive، وتتحقق من كل تقدم وتستأنف لاحقًا، ولا تدعي استرجاع التغييرات السابقة التي حُفظت قبل الفشل. لم يتغير سلوك الأدوار المخصصة أو المنع الصريح.
- التالي: استكمال اختبارات تبديل معرف المورد/الفرع لأسطح القراءة التي تغطيها حاليًا المراجعة الساكنة، ثم إعداد مصفوفة السياسة لمرحلة 2 دون تغيير صلاحيات تجارية غير معتمدة.

### متابعة تنفيذ — اختبارات IDOR لقراءات REST الحساسة

- أضيفت تغطية داخل الفرع وعبر الفروع لطابور دفعات الحجوزات، وسجل تمويل البيع، ووثائق التسليم، وقراءة طلب العميل المحتمل.
- اختُبرت نسختا REST `v1` و`v2`: القراءة داخل النطاق مسموحة؛ الطلبات المالية ووثائق التسليم عبر الفرع تعيد 404؛ طابور الإيداعات لا يتضمن معرف الدفعة الأجنبية؛ وموظف المبيعات غير المالك لا يقرأ طلب زميله حتى ضمن الفرع نفسه. بقي وصول المسؤول المصرح به متاحًا.
- لم يتطلب ذلك تعديلًا إنتاجيًا؛ تؤكد الخدمة الحالية حدود الفرع/المالك. نجحت `ADC_DATABASE_SCENARIOS_ONLY=1` بـ **849 تحققًا** في MariaDB مؤقتة معزولة، مع حذف قاعدة الاختبار وعدم استخدام قاعدة الموقع. اجتازت ملفات الاختبار المعدلة فحوص PHP و`git diff --check`.
- حدود هذه الشريحة: لا تمثل مصفوفة سلبية لكل المسارات أو الأدوار. التالي تقنيًا هو استكمال مصفوفة IDOR لبقية قراءات REST ذات الأولوية.

### متابعة تنفيذ — بقية قراءات REST المقيدة

- أضيفت اختبارات قراءة تكاليف الاقتناء: سماح لمستخدم ذي قدرة داخل فرعه، ومنع قراءة مركبة من فرع آخر في v1 وv2، ومنع مستخدم مبيعات لا يملك القدرة.
- اكتملت تغطية قراءة سجل الأنشطة في v1 وv2 لموظف غير مالك من الفرع نفسه، مع إثبات وصول المسؤول.
- اختُبرت تفضيلات الحساب في v1 وv2 لإثبات أن الاستجابة تخص المستخدم المصادق عليه ولا تعرض ارتباط عميل حساب آخر.
- اختُبرت قراءة مرشحي تطابق العملاء: السماح للمسؤول ورفض موظف عادي في نسختي REST.
- لا تعديل إنتاجي على هذه المسارات؛ تؤكد الاختبارات فحوص الخدمة والنطاق القائمة. نجح التشغيل المعزول `ADC_DATABASE_SCENARIOS_ONLY=1` بـ **862 تحققًا**، وأزيلت قاعدة الاختبار دون استخدام قاعدة الموقع؛ واجتازت ملفات الاختبار `php -l` و`git diff --check`.
- التالي: استكمال حالات HTTP للقوائم العامة/المشتركة وبقية بوابة العملاء وAJAX، ثم توثيق مدى اكتمال مصفوفة الاختبار. لا تغيير لصلاحيات الأدوار التجارية.

### متابعة التنفيذ — ذرية تخزين إدارة الصلاحيات

- توسعت `Transaction::begin()` لقبول قائمة جداول WordPress التي يجب أن تكون معاملية، والتحقق من محرك كل جدول في `information_schema` قبل فتح المعاملة. لا يبدأ التغيير إذا تعذر إثبات أن المحرك InnoDB.
- رُبط حفظ الدور وفصله عن مستخدميه بجدول `options`، وحذف الدور بجدولي `options` و`usermeta`، وتخصيص قدرات المستخدم بجدول `usermeta`. بقيت سلوكيات التفويض ومصفوفة القدرات دون تغيير.
- أُضيف fault injection معزول يحول `options` أو `usermeta` إلى MyISAM؛ ثبت أن حفظ الدور وتخصيص المستخدم يُرفضان دون كتابة، ثم أُعيدت الجداول إلى InnoDB. نجحت `ADC_DATABASE_SCENARIOS_ONLY=1` بـ **854 تحققًا**، ولم تُستخدم قاعدة الموقع. اجتازت ملفات PHP المعدلة `php -l` و`git diff --check`.
- التالي: توسيع التغطية إلى القراءات عبر بوابة العملاء وAJAX وبقية القوائم/القراءات المشتركة، مع إبقاء صلاحيات الأدوار التجارية كما هي.

### المرحلة 3 — الأساس المشترك والتوافق

**الهدف:** إعداد آلية موحدة بأقل تغيير ممكن، دون نقل كل المجالات دفعة واحدة.

**الأعمال:**

- توحيد سجل تعريف القدرات في البنية القائمة أو استخراج سجل مركزي إذا أثبت التدقيق الحاجة.
- تثبيت أسماء القدرات القديمة ومستهلكيها قبل أي إعادة تسمية؛ استخدام توافق انتقالي عند الضرورة.
- توحيد نقطة قرار التفويض أو تقوية المساعد الحالي؛ لا تنشأ طبقة جديدة إن كانت الحالية تغطي الحاجة.
- تعريف سياق المورد بطريقة موثوقة، ونتيجة رفض متوافقة مع نمط `WP_Error`/الاستجابات الحالي.
- توحيد تصنيف أخطاء عدم المصادقة وعدم التفويض وعدم وجود المورد بما لا يكشف وجود سجلات محمية.
- إنشاء/تحديث ترحيلات إصدارية متكررة بأمان وفق آلية الإصدار الحالية، لا عبر hook عشوائي جديد.
- ضمان بقاء تعريفات `adc_role_definitions` وتخصيصات المستخدم الفردية والمنح المباشرة قابلة للفهم والتراجع.

**المخرجات:** قاموس موحد مع توثيق الملكية، واجهة قرار تفويض متفق عليها، اختبار توافق، وترحيل تجريبي لا يغيّر سياسة العمل بعد.

**بوابة الخروج:** اختبارات وحدات للتفويض والتوافق ناجحة، وبيان واضح لكيفية استعادة حالة كل ترحيل.

### المرحلة 4 — موارد مشتركة: Scope والملكية والقراءة

**الهدف:** بناء قواعد الوصول للمورد والاستعلامات قبل توسيع صلاحيات الأدوار.

**الأعمال:**

- تطبيق تحقق المورد المحدد على معرفات Leads والمركبات وأوامر الشراء والمدفوعات وغيرها من الموارد الحساسة.
- فرض `own` و`assigned_to_me` و`branch` حيث يدعمها نموذج البيانات والسياسة المعتمدة.
- تطبيق عزل الفروع داخل قراءة المورد والاستعلامات والقوائم والتقارير والتصدير.
- منع الاعتماد على معرّفات المالك/الفرع المرسلة من المتصفح، والتحقق من ملكية المورد من مصدره المخزن.
- تحديد الحقول المسموح بها بحسب المجال والدور، ومنع تسريب الحقول الحساسة حتى عند السماح برؤية السجل.
- إضافة اختبارات معرفات موارد صحيحة/غير موجودة/خارج النطاق، مع منع تسريب وجود المورد عند اللزوم.

**المخرجات:** قواعد Scope قابلة للاختبار لكل نوع مورد، واستعلامات/واجهات قراءة ملتزمة بالنطاق.

**بوابة الخروج:** اختبارات سلبية لإساءة تبديل المعرفات والفروع لا تنجح في استرجاع بيانات، واختبارات قراءة صحيحة للمستخدمين المخولين تمر.

### المرحلة 5 — طرح الصلاحيات بحسب المجال (شرائح رأسية)

**الهدف:** نقل كل مجال من تعريف القدرة إلى الخدمة وAPI والواجهة واختباره معًا، دون تفعيل جميع الأدوار مرة واحدة.

تنفذ كل شريحة عبر البروتوكول نفسه: تحليل المستهلكين الحاليين → تحديث المصفوفة → ترحيل متوافق عند اللزوم → حماية الخدمة → حماية REST/المداخل الأخرى → تصفية البيانات → مواءمة UI → اختبارات موجبة وسلبية وتراجعية → مراجعة الفرق.

| الترتيب | الشريحة | أهم نقاط التحقق |
|---|---|---|
| 5.1 | Marketing وCRM | إنشاء/عرض العميل المسموح، تعديل الهوية والنشاط، منع تغيير المراحل والماليات والحذف غير المصرح، عزل الحملات والفروع |
| 5.2 | Sales | الموارد المسندة، عروض الأسعار، طلب الخصم، الحجوزات والأنشطة، منع الوصول خارج النطاق والاعتماد الذاتي المحظور |
| 5.3 | Sales Manager | نطاق الفرع، إدارة العملاء والإسناد، مراجعة الخصومات والاعتمادات فقط ضمن السياسة |
| 5.4 | Finance | تسجيل/التحقق من الدفعات، الاسترداد والمستندات، فصل الواجبات، منع الوصول إلى إجراءات المبيعات والمخزون |
| 5.5 | Inventory | العرض والإدارة والنقل وVIN والتسويات، منع المالية/المبيعات غير المخولة وتطبيق نطاق الفرع |
| 5.6 | Purchasing | دورة أمر الشراء، الإنشاء والتحرير والاستلام والاعتماد والإلغاء، وفصل المسؤوليات |
| 5.7 | Delivery | قائمة التسليم والتأكيد والإرجاع، منع تحول القدرة إلى إدارة مخزون عامة |
| 5.8 | Customer Service | بيانات وتفاعلات العميل والحجوزات المسموحة، مع عزل المجال والفرع |
| 5.9 | Auditor | قراءة فقط عبر كل واجهة وخدمة وAPI واستعلام، ومنع الكتابة المباشرة |
| 5.10 | General Manager | قدرات تشغيلية صريحة وحدود الاعتماد المثبتة، دون تجاوز شامل |
| 5.11 | محتوى وأدوار أخرى | التحقق من عدم كسر صلاحيات WordPress أو الأدوار المخصصة غير المذكورة |

**بوابة كل شريحة:** نجاح اختبارات الخدمة وHTTP وScope والبيانات والواجهة ذات الصلة، مع مراجعة فرق الملفات والتأكد من عدم تغيّر مسار تجاري خارج المطلوب. لا تبدأ الشريحة التالية عند فشل الاختبارات أو وجود قرار سياسة مفتوح.

### المرحلة 6 — الواجهات وسلامة واجهات API

**الهدف:** جعل الواجهة متسقة مع قرار الخادم دون اعتبارها حدًا أمنيًا.

**الأعمال:**

- إظهار أو إخفاء الإجراءات بحسب قرار التفويض نفسه وسياق المورد.
- حماية جميع REST routes الحساسة بـ`permission_callback` صريح، دون استبدال حارس الخدمة به.
- فحص `admin-post` وAJAX والروابط المباشرة والنماذج وكذلك مسارات العرض العامة.
- التأكد من أن استجابات REST والتقارير وملفات التصدير لا تحتوي حقولًا غير مخولة.
- ضمان أن عدم التفويض يعطي حالة/خطأ متوافقًا مع الأنماط الحالية، ولا يؤدي إلى fallback يسمح بالعملية.

**المخرجات:** واجهة متوافقة، وجدول مسارات API/المعالج وحارس كل منها، واختبارات وصول مباشرة.

**بوابة الخروج:** الطلب المباشر الذي يتجاوز UI مرفوض، والطلب المخول ينجح دون اعتماد على بيانات عميل موثوقة.

### المرحلة 7 — التدقيق التشغيلي ومراقبة الانتقال

**الهدف:** تسجيل الأدلة اللازمة ومراقبة الانتقال دون تعطيل سير العمل.

**الأعمال:**

- استخدام خدمة سجل التدقيق الحالية إن كانت مناسبة، وإضافة أقل الحقول الناقصة فقط.
- تسجيل الفاعل والفعل والقدرة والمورد والفرع والنتيجة والوقت، والتغييرات القديمة/الجديدة والسبب حيث تكون آمنة وضرورية.
- إعطاء الأولوية للإسناد، وتغيير الحالة، والتسعير/الخصم، والمدفوعات/الاسترداد، وVIN، والنقل/التسوية، واعتماد الشراء، والتسليم، وتغيير الصلاحيات.
- عدم تسجيل أسرار أو بيانات دفع كاملة أو معلومات شخصية زائدة؛ تحديد الاحتفاظ والوصول لسجل التدقيق وفق السياسة.
- عند وجود آلية انتقال، مراقبة محاولات الاستدعاء القديمة أو الرفض المتوقع دون السماح المؤقت بعملية غير مصرح بها.

**بوابة الخروج:** سجلات قابلة للتحقق للعمليات الحساسة، وعدم وجود بيانات سرية زائدة أو فجوات تمنع التحقيق.

### المرحلة 8 — الإزالة التدريجية للقديم والإطلاق

**الهدف:** إزالة التكرار أو القدرات القديمة فقط بعد إثبات عدم استخدامها.

**الأعمال:**

- حصر مراجع كل قدرة/حارس قديم بما في ذلك الإضافات والأدوار المخصصة والبيئات المتعددة المواقع عند انطباقها.
- تشغيل تقرير مقارنة قبل/بعد لترحيل القدرات، مع قائمة ما سيضاف أو يبقى أو يزال وسبب كل قرار.
- إزالة ترحيلات أو قدرات obsolete فقط في إصدار منفصل، وبعد تأكيد عدم وجود مستهلك أو تخصيص يدوي.
- تحديث سجل التغييرات والتوثيق ومصفوفة الأدوار وإرشادات الدعم.
- إطلاق مرحلي على بيئة اختبار ثم staging ثم إنتاج وفق إجراءات النشر الحالية، مع خطة إيقاف/استعادة واضحة.

**بوابة الخروج:** موافقة المالك، نتائج الاختبارات النهائية، تحقق سجل الترحيل والتراجع، وعدم وجود صلاحيات مكسورة أو توسيع نطاق غير مقصود.

## 9. استراتيجية الترحيل والتراجع

### قبل الترحيل

- توثيق نسخة الإضافة/المخطط وآلية الترحيل القائمة ومفاتيح الإصدارات المستخدمة.
- أخذ نسخة احتياطية قابلة للاستعادة من خيارات الأدوار وصلاحيات المستخدمين والبيانات التي ستتأثر، في بيئة آمنة.
- تسجيل الفروق المتوقعة للأدوار والمستخدمين والتعريفات المخصصة؛ لا تُخزن بيانات حساسة في سجلات عامة.
- تجربة الترحيل على نسخة معزولة من بيانات اصطناعية/منزوعة الحساسية.

### أثناء الترحيل

- ترحيل إصدارِي، متكرر بأمان، محدود الأثر وقابل للرصد؛ يتبع lifecycle الموجود في المشروع.
- الحفاظ على القدرات القديمة خلال فترة التوافق إذا احتاج المستهلكون إلى ذلك؛ لا تُلغى إلا بعد ترحيل المستهلكين والتحقق.
- عدم استبدال مصفوفة الدور يدويًا إذا كانت تعريفات المشرفين أو المستخدمين المخصصة هي المرجع الحالي.
- عدم تغيير مخطط قاعدة البيانات إلا بعد إثبات أن النموذج لا يمثل scope/ownership المطلوب، مع خطة مستقلة للبيانات.
- عدم إخفاء فشل قاعدة البيانات أو الترحيل عبر نجاح شكلي؛ تسجل الأخطاء وتوقف الخطوة المتأثرة بأمان.

### التراجع

- يجب أن يحدد كل ترحيل مسبقًا ما الذي يمكن عكسه وما الذي لا يمكن عكسه.
- إزالة المنح التي أضافها الترحيل فقط عندما يمكن إثبات ملكيتها له، وعدم حذف منح أضيفت يدويًا أو بواسطة إضافة أخرى.
- استعادة نسخة الخيارات/البيانات الموثقة عند الحاجة، وإرجاع الكود إلى إصدار متوافق عبر إجراءات النشر القياسية.
- إن كان التراجع قد يعيد ثغرة، أوقف العمليات المتأثرة أو استخدم وضعًا آمنًا محددًا بدل إعادة فتح الصلاحية بلا حارس.
- اختبار التراجع وإعادة التشغيل على البيئة المعزولة قبل الإنتاج.

## 10. خطة الاختبارات والتحقق

تُضاف الاختبارات إلى البنية الموجودة، ولا يستبدل أي اختبار حالي ولا ينشأ إطار جديد دون ضرورة مثبتة.

### طبقات الاختبار

1. **اختبارات وحدات:** قاموس القدرات، ربط الدور، القرار عند غياب القدرة، الحدود، أخطاء السياق.
2. **اختبارات الأدوار:** سماح/منع لكل فعل مع الدور الفعلي، بما فيه أدوار مخصصة وتخصيصات فردية.
3. **اختبارات النطاق:** المالك، المسند إليه، الفرع الحالي، فرع آخر، نطاق المؤسسة إذا كان معتمدًا، والمورد بلا نطاق موثوق.
4. **اختبارات الخدمة:** تحقق مستقل حتى عند استدعاء الخدمة مباشرة دون API أو واجهة.
5. **اختبارات HTTP/API:** طلبات مباشرة للمسارات، بما فيها المستخدم غير المسجل، مستخدم بلا قدرة، مستخدم خارج النطاق، والمستخدم المصرح.
6. **اختبارات البيانات:** إخفاء الحقول المالية/الحساسة، والقوائم والتقارير والتصدير دون تسريب سجلات خارج النطاق.
7. **اختبارات UI:** ظهور الإجراء للمخول وإخفاؤه لغير المخول، مع اختبار أن الطلب المباشر يبقى محميًا.
8. **اختبارات ترحيل:** تطبيق مرتين، حفظ التخصيصات، الفشل الجزئي، التراجع، إعادة التشغيل، والأدوار غير المعروفة.
9. **اختبارات أمنية سلبية:** تبديل معرف مورد، تزوير المالك/الفرع/الدور، الوصول بين الفروع، استدعاء endpoint مباشرة، والكاتب بدور Auditor.
10. **اختبارات انحدار:** تشغيل الاختبارات الحالية ذات الصلة بالمسارات التجارية، الحسابات، المخزون، المالية، الأدوار، وREST.

### جدول تقاطعي أساسي

يُستخدم الجدول الآتي كنقطة بداية ويُستكمل من المصفوفة المعتمدة؛ جميع حالات المنع يجب اختبارها في الخدمة وواجهات الدخول ذات الصلة، لا في UI فقط.

| المحاولة | النتيجة المتوقعة |
|---|---|
| Marketing يغير مرحلة بيع أو يعتمد سعرًا/خصمًا أو يسجل دفعة | رفض |
| Marketing يصل إلى Lead غير مخول أو فرع غير مصرح | رفض وعدم كشف البيانات |
| Sales يصل إلى عميل غير مسند/فرع آخر أو يدير المالية/المخزون | رفض |
| Sales يعتمد طلبه بنفسه حين تشترط السياسة فصل الاعتماد | رفض |
| Finance ينفذ تغيير مرحلة بيع أو تعديل مخزون/سعر | رفض ما لم تمنح قدرة مستقلة معتمدة |
| Inventory ينفذ عملية مالية أو اعتماد بيع | رفض |
| Delivery ينفذ إدارة مخزون عامة أو عملية مالية | رفض |
| Auditor يرسل أي طلب كتابة مباشرة | رفض |
| مستخدم يزوّر `user_id` أو `branch_id` أو `role` في الطلب | لا يغير قرار التفويض |
| مستخدم مخول يقرأ/يعدل موردًا خارج النطاق عبر تغيير المعرف | رفض |
| Admin أو `manage_options` يصل إلى إعداد WordPress النظامي | يحافظ على السلوك الإداري المقصود |
| تغيير مستخدم لدوره مع تخصيص فردي/بدونه | يحافظ على قواعد التوريث الموثقة |

### التحقق البرمجي

- تشغيل `php -l` لكل ملف PHP متغير.
- تشغيل اختبارات PHP/قاعدة البيانات/HTTP القائمة والمحددة لكل مرحلة باستخدام أوامر المشروع الفعلية.
- تشغيل اختبارات واجهة المستخدم ذات الصلة عند وجود harness متاح.
- فحص `git diff --check` ومراجعة الفرق يدويًا، بما في ذلك أي migration أو route جديد.
- توثيق الأمر الدقيق والنتيجة الفعلية؛ لا يعلن النجاح دون نتائج.

## 12. الحوكمة والتوثيق المطلوب

تُحدّث الوثائق القائمة بعد اعتماد نتائج التدقيق والتنفيذ. تُحسم أماكن الملفات النهائية وفق نمط المشروع، مع تجنب نسخ متضاربة. يجب أن تغطي الوثائق:

- قاموس القدرات ومعانيها ومستهلكيها.
- المصفوفة المعتمدة للأدوار والقدرات والنطاقات والقيود.
- تدفق القرارات والاعتمادات وحدودها ومصدر السياسة.
- تغطية REST والخدمات وصفحات الإدارة والحقول الحساسة.
- تاريخ الترحيلات، التوافق، التراجع، واختبارات كل إصدار.
- آلية طلب صلاحية جديدة ومن يراجعها ويعتمدها.

## 13. تعريف الإنجاز (Definition of Done)

لا تعتبر إعادة التوحيد مكتملة حتى تتحقق جميع البنود التالية:

- [ ] اكتمل تدقيق القراءة فقط واعتمدت نتائجه.
- [ ] اعتُمدت مصفوفة الأدوار والقدرات والنطاق والحدود التجارية.
- [ ] لا توجد عملية حساسة بلا قدرة ونطاق وحارس خدمة موثق.
- [ ] كل REST route حساس له `permission_callback` مناسب، والخدمة محمية بصورة مستقلة.
- [ ] ملكية الموارد وعزل الفروع يتحققان على مستوى المورد والاستعلام، لا الواجهة فقط.
- [ ] الاستجابات والتقارير والتصدير لا تكشف حقولًا أو سجلات خارج الصلاحية.
- [ ] لا يستخدم `manage_options` كتجاوز لعمليات العمل.
- [ ] يلتزم Auditor بالقراءة فقط على كل مسار.
- [ ] ترحيلات الأدوار والمستخدمين المخصصة قابلة لإعادة التشغيل والتراجع ولا تمحو تعديلات يدوية.
- [ ] اختبارات السماح والمنع وIDOR والفروع والـ API والخدمات وUI والترحيل والانحدار ناجحة.
- [ ] فحوص PHP والفرق البرمجي ناجحة، ولا توجد تغييرات غير مرتبطة.
- [ ] سجل التدقيق يغطي العمليات الحساسة دون تخزين أسرار أو بيانات غير لازمة.
- [ ] التوثيق وسجل التغييرات وخطة الإطلاق والاستعادة محدثة.

## 14. بروتوكول التنفيذ والتقرير

لكل مرحلة تنفيذية، الترتيب الإلزامي:

```text
1. Inspect — فحص الملفات والمسارات والاختبارات ذات الصلة
2. Confirm — تثبيت السياسة والنطاق وعدم وجود قرار معلق
3. Plan — تحديد الملفات والتغيير والمخاطر والاختبارات
4. Change — أصغر تغيير متماسك للمرحلة
5. Syntax — فحص بناء PHP
6. Tests — اختبارات الوحدة/الخدمة/API/الأمن والانحدار ذات الصلة
7. Diff review — مراجعة الحراس والترحيل والبيانات والتوافق
8. Report — توثيق النتائج والقيود والخطوة التالية
```

قالب التقرير:

```text
PHASE:
STATUS:
FILES INSPECTED:
FILES CHANGED:
CAPABILITIES ADDED/CHANGED/REMOVED:
AUTHORIZATION AND SCOPE CHANGES:
MIGRATION AND ROLLBACK:
TESTS RUN:
PASSED / FAILED:
REGRESSION STATUS:
BACKWARD COMPATIBILITY:
OPEN DECISIONS / RISKS:
NEXT GATE:
```

لا تنتقل إلى المرحلة التالية عند فشل اختبار، أو وجود تعارض غير محلول، أو عدم معرفة أثر الترحيل.

## 15. القرار المطلوب قبل التنفيذ

`ContentTransfer`: رفض الصلاحية والـnonce للتصدير والمعاينة والتطبيق، ورفض المراجعة القديمة دون تغيير، وتنظيف المرفقات عند فشل التطبيق؛ نجحت **91 فحصًا** في `ADC_CATALOG_ONLY=1`. كما اكتملت اختبارات HTTP لمعالج `adc_save_technical_options`، بما فيها الحفظ الصحيح ورفض المراجعة القديمة، ونجحت **95 فحصًا** في المجموعة نفسها. واكتمل فحص `adc_save_vehicle_colors` باختبارات الصلاحية والـnonce والمدخلات والمراجعة القديمة وثبات بيانات Onyx؛ نجحت **101 فحصًا** في المجموعة المعزولة. وأضيفت اختبارات HTTP لمعالج `adc_save_social_channels` للرفض والتحقق والحفظ والتراجع عند فشل التدقيق؛ انتهت المجموعة بـ **107 فحوص نشر HTTP** ونجحت اختبارات حفظ الخدمة الثمانية. واكتملت اختبارات HTTP لمساري `adc_followup_email` و`adc_ack_followup`، بما يشمل رفض الدور والـnonce والحالة القديمة، نجاح الحفظ مع التدقيق، فشل التدقيق؛ اجتازت مجموعة لوحة المخزون المعزولة **40 فحصًا**، دون تعديل إنتاجي. نُظفت fixtures وقواعد وخوادم الاختبار دون الاتصال بقاعدة الموقع.
