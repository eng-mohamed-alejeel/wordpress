# CRM intake and request workflow — 1.15.0–1.29.0

## Lead claim, first-contact and stage history — schema 1.29.0

The additive CRM schema now records `claimed_at`, `first_contact_at`, a reference to the first-contact activity and lead priority. Activity rows can retain a structured outcome and the time the interaction occurred. Employees can set low, normal, high or urgent priority on an accessible lead; queue results order by priority and then age. On the next normal plugin load, the existing schema installer runs `dbDelta` and verifies these additions; it does not rewrite existing leads or backfill historical contact evidence. Existing `assigned` records with no `claimed_at` are deliberately excluded from automatic release until an administrator reviews them.

Sales employees can see unassigned `new` leads for active assigned branches in their shared queue. The queue displays name, phone, creation time and priority; unassigned leads are excluded from their owned-lead table, direct detail view and activity history. The list API masks email, city, campaign, platform and creator for unassigned new records. Claim uses a locked row and a conditional update; it writes the owner, `assigned` stage, claim time, activity and audit event in one transaction.

Only the first-contact action can establish first-contact evidence. It requires a supported contact type, local date/time, outcome and notes; it stores the occurrence in UTC, adds an activity, sets `first_contact_at`, and advances `assigned` to `contacted` atomically. A generic activity or stage request cannot substitute for it. The manager release operation returns only an uncontacted `assigned` lead to `new` and requires a reason. Reassignment of an already-owned lead also requires a reason. The existing stale-claim job checks `claimed_at` and `first_contact_at`, locks and rechecks each lead before release, and records activity/audit. It processes at most 100 candidates per run. WP-Cron can be late on low-traffic sites; a real system scheduler should request `wp-cron.php` if the policy requires tighter timing.

The additive `lead_stage_history` table records the initial stage and each actual stage change in the same transaction as the lead mutation. Rows retain branch and owner attribution at transition time and the duration since the previous recorded stage, chosen by event timestamp rather than insertion order. A bounded, resumable and idempotent background job backfills transitions only from matching append-only audit events (`lead.created`, claims, assignments, first contact and stage changes); it does not infer transitions from the current lead row or generic activity notes. Schema installation schedules this work rather than processing a batch synchronously during a user request. It also recalculates existing durations in bounded lead batches so previously stored intervals use chronological event order. The CRM performance page shows the event cursor, audit-event count, duration-recalculation progress, and retry status. Recovered rows retain the audit event ID. Stage history already written by the new service is linked to its matching audit event rather than duplicated. Any period without reliable audit evidence remains unavailable, and the first audited event may have unknown elapsed time if the initial stage itself was not audited.

When an uncontacted claim expires, its release, stage-history entry, activity, audit record and durable owner/branch-manager inbox notifications are committed together. Email uses the existing administrator-controlled follow-up email setting and shared retryable outbox. If notification persistence fails, the lead remains assigned and the scheduled release can retry. The notification contains no customer identity or contact data.

## Assignment policy — settings section `crm`

Manual assignment remains the default. An administrator can enable branch-based round robin and configure the claim timeout from 5 to 1440 minutes. When enabled, new leads for an active branch are assigned only to users with the `dealership_sales` role, the own-lead capability, and an active assignment to that branch. The branch row is locked inside the intake transaction so simultaneous submissions rotate in order; assignment, activity and audit are committed with the lead. If no eligible sales employee exists, the lead remains unassigned in that branch's shared queue. Lead intake without a branch is never auto-assigned.

WP-Cron timing caveats still apply to expiry enforcement and the bounded audit backfill. No live production database was opened or migrated as part of this change; validate the existing schema and take a database/files backup on staging before rollout.

## CRM filters and performance report

The lead list and its count share validated filters for stage, priority, source, branch, owner and overdue follow-up. Branch and owner selectors are only shown to staff with branch-lead visibility; service queries still enforce the caller's assigned branch scope, including for crafted query parameters. The CSV export carries the same priority, branch and owner filters.

Users with `adc_view_reports` can open CRM performance from the operations workspace. Date-bounded aggregate tables show leads by branch and salesperson, first-contact count and average elapsed time from lead creation, overdue follow-ups, won/lost totals and current stage distribution. Date boundaries use the WordPress site timezone and are converted to UTC for storage queries. These cohort metrics include leads created during the selected period; current-stage and overdue counts reflect the state at report time, not only events occurring during that period. A separate historical table groups actual stage transitions by branch, owner at transition time and stage pair, showing transition/lead counts, each destination's share among distinct leads leaving the same source stage, and average time in the preceding recorded stage. A single destination share cannot exceed 100%; the sum across destinations may exceed 100% when the same lead reaches different destinations or revisits a stage during the period. Reports contain no customer identity fields, cap the selected range at 366 days, and use the existing branch-scope policy. Historical transition rows include only verified audit-derived and newly recorded stage changes.

The marketing intake uses one form. Campaign/source attribution, consent, creator, referral time, optional branch-valid salesperson assignment, activities, stage history and audit records are committed with the lead. The form carries an idempotency key to make safe retries return the original lead. Queue and board views are paged in bounded batches of 100; CSV export streams every matching authorized result in pages rather than silently stopping at the first 100.

Due CRM follow-ups use the shared durable notification inbox and outbox: owners are notified, branch managers receive escalation after 24 hours, email is an administrator-controlled option, and delivery failures remain retryable and observable. Claim-expiry events notify the former owner and branch managers immediately. Delivery does not include customer names or contact details.

## Implemented boundary

- `PublicIntake` validates public REST and theme contact/test-drive requests. `ContactIdentity` normalizes Saudi numbers, Arabic/Persian digits and email and requires explicit marketing consent.
- A public name, phone or email is unverified input. Guest and generic REST enquiries create separate contacts; matching values never grant account ownership or cause an automatic merge. Since 1.17.0, authenticated theme intake reuses a contact by the server-owned account ID.
- Logged-in theme requests use the current account's name, email and saved phone. Customers missing a phone update their account profile before submitting. REST contact fields remain enquiry input and do not link accounts by email.
- Customer, lead, initial notes, optional theme request copy and audit commit together. The compatibility table must be InnoDB. Failure rolls back the complete write. Duplicate unique replay keys roll back the losing transaction before looking up the original acknowledgement.
- The existing AJAX action names, nonce and booking response fields remain supported. Customer-account reads continue using the theme tables. New core-owned requests skip the duplicate `cd_crm` request capture.
- Scoped activity history is available from CRM → سجل متابعة الفرصة and `GET /leads/{id}/activities`. Notes include the enquiry type, vehicle post, requested appointment and message. Activity creation updates the lead timestamp and any supplied next action.

## Replay and abuse controls

Forms load a separate plugin script; the theme's `main.js` is unchanged by this increment. The script creates a secure UUID before the theme builds FormData and retains it after failed submissions. Changing the form payload or resetting the form creates a new request key. A page reload loses the in-memory key; browsers without cryptographic random bytes submit without a key. External clients should persist a UUID per intended submission.

The server stores only HMACs of the authentication identity/key and canonical payload. Replays reveal the original lead ID and acknowledgement, never customer details or its current sales stage. A changed payload with the same UUID returns 409. Rotating the WordPress authentication salt changes the key namespace; replay across rotation is not guaranteed. Privacy erasure removes the payload fingerprint, causing old replays to conflict instead of restoring erased data.

Both public entry points share the atomic `intake` policy with an eight-attempt hourly limit and a honeypot. Validated attempts are assigned exactly through an InnoDB fixed-window bucket before persistence. Anonymous identity starts from `REMOTE_ADDR`; forwarded headers are ignored unless the direct peer matches a bounded exact/CIDR list supplied by `adc_trusted_proxy_cidrs`. Authenticated callers use their WordPress user ID. Only an HMAC bucket is stored. Storage failure returns 503 instead of bypassing protection. Validation/rate checks precede replay. This mechanism prevents matching retries that reach persistence; it does not promise acceptance after vehicle availability, appointment time or configuration changes. Production edge/WAF controls and actual proxy configuration remain release work; see `SECURITY-HARDENING.md`.

## Privacy and compatibility

WordPress erasure clears contact identifiers, activity text/schedule, legacy request content and the public payload fingerprint. The scheduled retention job also anonymizes linked theme copies transactionally, only when they are completed/cancelled and older than the retention cutoff. Active or recently updated copies, SQL failures and non-InnoDB storage prevent that customer from being anonymized. Quote/sale operational retention rules continue to apply.

In 1.16.0, linked request replies, cancellation and rescheduling use `RequestWorkflow` from both the theme adapter and core REST/admin forms. These updates append core activity notes and audit records transactionally. Earlier legacy updates are not backfilled. In 1.17.0, automatic duplicate theme account-profile creation/synchronization stops while the core identity class is present. Version 1.18.0 retires only legacy profiles carrying the linked account ID, provides administrator read-only access and synchronizes profile/preferences. Historical contact-based claims and financial merges remain outside these increments.

## Linked request workflow (1.16.0)

Open CRM → سجل متابعة الفرصة and select a lead. If it has a compatibility message/booking, the embedded form shows its status, reply and appointment. View-only users cannot submit the edit form. Sales staff manage owned leads in active assigned branches; branch managers manage leads in their branch scope. Global administrators can triage branch-zero records. The same form is embedded in the existing theme request table when its menu is accessible.

Staff writes require a current opaque revision covering the request row and latest core activity ID. The service locks the customer, lead and compatibility request, then checks the revision against current activity state. Concurrent edits or stale tabs return 409 rather than overwriting newer content. Exact no-op submissions do not add activity/audit rows. Customer cancellation uses the authenticated recorded account ID, never an email match or a submitted user ID, and repeated cancellation is harmless.

Messages move from new to read/completed/cancelled, or read to completed/cancelled. Bookings move from pending to confirmed/cancelled, or confirmed to pending/completed/cancelled. Closed requests can receive a reply correction but cannot reopen or reschedule. New/changed active appointments must be in the future in the site timezone. Confirmation/rescheduling rechecks availability; mapped operational vehicles must still belong to the lead's active branch. Changing a test-drive request does not change a vehicle reservation, lead stage or generic follow-up date.

Request text and appointment changes are recorded in erasable activity notes. The audit contains the request reference, old/new status, activity ID, changed field names and customer/staff action classification. A compatibility update, activity insert, lead update or audit failure rolls back the operation. The compatibility table must be InnoDB.

Theme request tables, related-request lists and dashboard message/booking counters use the core view scope in SQL, including pagination totals. Unmapped legacy requests lack a branch/owner relationship and are read-only while the 1.29.1 ownership boundary is enabled. Core sales roles use the plugin CRM form without requiring the theme's `manage_car_dealer` capability. Old CRM profile contents are preserved as private history and are not converted into active records.

The authenticated-request reconciliation cursor now advances past core-owned requests without recreating legacy CRM records. Schema/storage lookup errors stop processing rather than treating a mapped request as legacy. Disabling the public intake switch does not disable authorization/auditing of already-linked requests.

The 27-check real-theme journey closes date-only/time-only rescheduling, mapped vehicle branch rejection, targeted merge/privacy races, legacy cursor progress, scoped table/count pagination and the customer account/browser path. ## Rollout and reversal

1. Preserve the current database/files backup and apply the additive schema 1.12.0 upgrade through the existing installer. Verify its marker and compatibility/user-table engines on an isolated/staging copy before operational use.
2. The `adc_core_public_intake_enabled` filter defaults to true. Returning false switches theme creation submissions back to the pre-existing theme handlers and disables the plugin form script. Public REST intake still uses core validation; linked request updates retain the 1.16.0 service boundary and duplicate CRM capture remains suppressed. This is a theme intake switch, not a schema downgrade or reversal of recorded requests.
3. Keep both core and theme rows during the review window. No table deletion, automatic merge, backfill or source-data import is part of this increment. Before reverting plugin code, assess the additive schema and changed phone/source contracts; do not delete the replay columns to make a version marker match.
4. Review the passing local evidence and remaining limits in `VERIFICATION-1.17.0.md` and `ACCOUNT-JOURNEY-VERIFICATION.md` before operational use. Current synthetic coverage establishes the listed intake, identity, workflow, rollback, responsive account journey and targeted concurrency behavior.
