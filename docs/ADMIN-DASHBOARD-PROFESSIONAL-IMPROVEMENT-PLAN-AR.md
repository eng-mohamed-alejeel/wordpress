# خطة التحسين الاحترافية الشاملة للداشبورد الإداري

**الإصدار المرجعي:** 1.66.0  
**الحالة:** جاهزة للتنفيذ المرحلي  
**النطاق:** `wp-admin/admin.php?page=adc-workspace` وجميع صفحات الإدارة التابعة للإضافة، مع الحفاظ على المسارات العامة والحسابات الشخصية خارج نطاق الداشبورد.  
**الخطة السابقة:** [خطة إعادة تنظيم لوحة الإدارة والصلاحيات](ADMIN-DASHBOARD-EXECUTION-PLAN-AR.md)

## 1. الهدف

رفع جودة الداشبورد من واجهة مستقرة ومختبرة إلى نظام إداري احترافي قابل للتوسع، بحيث يكون:

- واضحًا لكل دور وحساب وفرع.
- أسرع في التحميل والتنقل.
- موحدًا بصريًا بين CRM والتقارير والسياسات والمخزون وOnyx.
- قابلًا للاستخدام بلوحة المفاتيح وقارئات الشاشة.
- قابلًا للمراقبة والتشخيص قبل ظهور المشكلة للمستخدم.
- قابلًا للنشر المتكرر دون كسر الصلاحيات أو البيانات أو الروابط القديمة.

## 2. ما تم إنجازه وما لن يُعاد فتحه

تم إنجاز واختبار إعادة تنظيم التنقل، مساحة العمل، الصلاحيات المرئية، RTL/LTR، الوضع الداكن، دعم الجوال، صفحات التقارير والسياسات وOnyx، واختبارات الحزمة والتثبيت.

لا تتضمن هذه الخطة:

- إعادة كتابة الداشبورد من الصفر.
- تغيير جداول الأعمال أو نقل البيانات.
- تغيير صلاحيات الحسابات الحقيقية تلقائيًا.
- حذف روابط قديمة دون مسار توافق واختبار.
- استبدال WordPress Admin بالكامل.

كل دفعة لاحقة يجب أن تكون صغيرة، قابلة للعكس، ومحمية باختبار قبل الانتقال إلى الدفعة التالية.

## 3. مبادئ التنفيذ الإلزامية

1. لا تعديل على قاعدة بيانات الموقع الحقيقية أثناء الاختبارات.
2. لا تعديل على أدوار أو فروع الحسابات الحقيقية دون سجل اعتماد واضح.
3. التحقق الخادمي من الصلاحية والنطاق يسبق إظهار الصفحة أو الإجراء.
4. لا يعتمد الأمان على إخفاء عناصر القائمة فقط.
5. كل صفحة جديدة تستخدم مكونات CSS المشتركة بدل إضافة أنماط خاصة بلا حاجة.
6. كل استعلام جديد في التقارير يملك حدودًا واضحة للصفحات والتاريخ والنطاق.
7. كل دفعة تنتهي باختبار PHP، JavaScript، المتصفح، الجوال، الصلاحيات، والحزمة.
8. لا يتم اعتماد نتيجة اختبار تستخدم بيانات تجريبية خارج بيئة معزولة.

## 5. AD-040 — خط أساس الأداء

### الهدف

قياس الوضع الحالي قبل تحسينه حتى لا يتم اعتماد انطباعات بصرية غير قابلة للإثبات.

### الصفحات المستهدفة

- مساحة العمل.
- CRM والتقارير العامة وتقارير CRM.
- السياسات والإعدادات.
- المخزون وOnyx.
- المشتريات والمالية والتسليم.
- شاشة الأدوار ومراجعة الوصول.

### ما يجب قياسه

- زمن الاستجابة الخادمية TTFB.
- زمن اكتمال DOM والتحميل الكامل.
- حجم CSS وJavaScript المحمّل لكل صفحة.
- عدد الاستعلامات وزمن أبطأ 10 استعلامات.
- حجم HTML النهائي.
- عدد العناصر المرئية في القائمة والصفحة.
- زمن تحميل الجداول والتقارير.
- معدل أخطاء JavaScript وPHP.

### المخرج

إنشاء تقرير خط أساس في:

`docs/artifacts/admin-dashboard-performance-baseline-1.66.0/`

ويجب أن يتضمن الجهاز، إصدار PHP، حجم البيانات، الدور، الفرع، اللغة، العرض، ونتائج كل صفحة.

### معيار القبول

- وجود قياس قابل لإعادة التشغيل لكل صفحة مستهدفة.
- عدم تغيير السلوك الوظيفي أثناء القياس.
- عدم استخدام قاعدة الموقع الحقيقية إذا احتاج الاختبار إلى بيانات إضافية.

### نتيجة AD-040 — خط الأساس المعتمد

اكتمل القياس الفعلي عبر 64 حالة: 16 صفحة إدارية، العربية والإنجليزية، وعرض 1440 و390px. نجحت الحالات كلها دون أخطاء PHP أو JavaScript، أو موارد CSS/JavaScript فاشلة، أو اختلاف RTL/LTR، أو overflow عام.

النتائج المرجعية الحالية:

- TTFB: الوسيط `143.35ms`، وP95 `185ms`.
- DOMContentLoaded: الوسيط `642.95ms`، وP95 `765.4ms`.
- اكتمال التحميل: الوسيط `650.15ms`، وP95 `784.9ms`.
- First Contentful Paint: الوسيط `310ms`، وP95 `376ms`.
- النقل الشبكي: الوسيط `4,510,782` بايت، وP95 `4,550,099` بايت.
- الموارد: الوسيط `88` موردًا، وP95 `89` موردًا لكل صفحة.

أكبر مصدر قابل للتحسين ظهر في جميع الحالات هو موارد WordPress الأساسية الخاصة بمحرر البلوكات: `block-editor.min.js` بحوالي `1.41MB`، و`components.min.js` بحوالي `837KB`، إضافة إلى `load-styles.php` بحوالي `549KB`. لا يُحذف أي مورد قبل إثبات تبعيته واختبار المسارات الأصلية؛ تتم مراجعة ذلك في AD-041 وAD-043 عبر تحميل مشروط ومقارنة وظيفية.

حُفظت البيانات التفصيلية القابلة للمقارنة في [baseline.json](artifacts/admin-dashboard-performance-baseline-1.66.0/baseline.json)، كما أضيفت أداة إعادة القياس [browser-admin-performance-baseline.cjs](../wp-content/plugins/auto-dealership-core/tests/browser-admin-performance-baseline.cjs). أضيف قياس SQL لاحقًا في AD-043 بوضع قراءة فقط مع حارس كتابة، بينما يبقى القياس المعتمد على نسخة معزولة مماثلة للإنتاج خطوة تحقق لاحقة.

## 6. AD-041 — نظام التصميم والمكونات المشتركة

### الهدف

تقليل اختلاف المظهر بين الصفحات وتقليل اعتمادها على قواعد CSS مكررة أو متعارضة.

### التنفيذ

1. تعريف tokens مركزية للألوان، المسافات، نصف القطر، الظلال، الخطوط، حالات التركيز، والحدود.
2. اعتماد مكونات مشتركة بأسماء واضحة، مثل:
   - `.adc-panel`
   - `.adc-card-grid`
   - `.adc-table-scroll`
   - `.adc-form-grid`
   - `.adc-field`
   - `.adc-status-badge`
   - `.adc-empty-state`
   - `.adc-notice`
   - `.adc-action-row`
3. نقل الأنماط المتكررة من `admin.css` إلى طبقة مكونات واضحة دون تغيير أسماء الصفحات الحالية دفعة واحدة.
4. تحديد ترتيب تحميل ثابت للأنماط:
   - القواعد الأساسية.
   - الهيكل الإداري.
   - مكونات الإضافة.
   - مساحة العمل.
   - تخصيص CRM أو الصفحة عند الحاجة.
5. منع `style=` داخل قوالب الإدارة إلا لحالة ديناميكية لا يمكن تمثيلها بفئة CSS.
6. إضافة دعم واضح لـ RTL/LTR والوضع الداكن لكل مكون.

### الملفات المتوقعة

- `assets/css/admin.css`
- `assets/css/admin-structure.css`
- `assets/css/admin-workspace.css`
- `assets/css/crm-admin.css`
- ملفات صفحات الإدارة التي تحتوي قوالب مخصصة.

### معيار القبول

- عدم وجود تكرار مرئي بين CRM والتقارير والسياسات وOnyx.
- نجاح اختبار الفتح والداكن وRTL/LTR.
- عدم وجود overflow عام عند 320 و390 و768 و1440px.
- نجاح اختبار التباين لجميع النصوص المرئية.

### نتيجة AD-041 — نظام الألوان والمكونات المشتركة

اكتملت الدفعة دون تغيير أي إعداد محفوظ في قاعدة البيانات أو ألوان التخصيص الفعلية. تم ربط طبقة `adc-*` الدلالية مباشرة بمتغيرات `BrandPalette` الحالية (`--ab-*`) حتى تستجيب الصفحات للون المخصص والوضع الداكن دون ألوان ثابتة داخل الطبقة المشتركة.

ما تم تنفيذه:

- توسيع aliases الألوان المشتركة في [admin-tokens.css](../wp-content/plugins/auto-dealership-core/assets/css/admin-tokens.css) لتشمل النص والعناوين والحواف والتركيز والحالات والسطوح والأزرار.
- إزالة fallbackات الألوان الثابتة من [admin-structure.css](../wp-content/plugins/auto-dealership-core/assets/css/admin-structure.css) وربط البطاقات والشارات والمقدمة والظلال بالمتغيرات الدلالية.
- منع قاعدة روابط الإدارة العامة من تجاوز ألوان بطاقات مساحة العمل في [brand-ui.css](../wp-content/plugins/auto-dealership-core/assets/css/brand-ui.css).
- تضييق قاعدة `:read-only` في [brand-fields.css](../wp-content/plugins/auto-dealership-core/assets/css/brand-fields.css) حتى لا تُعامل أزرار الإرسال كحقول قراءة فقط، مع الحفاظ على مظهر الحقول النصية المقفلة.
- إضافة [browser-admin-color-contract.cjs](../wp-content/plugins/auto-dealership-core/tests/browser-admin-color-contract.cjs) لاختبار تدفق الألوان من التخصيص إلى المكونات دون حفظ أي قيمة.

نتائج التحقق:

- عقد الألوان: `96/96` تحقق ناجحًا عبر 6 مسارات، الوضع الفاتح والداكن، و1440/390px.
- التباين البصري: 9 مسارات، وضعان، و`0` إخفاقات.
- قبول لوحة الإدارة: `162` تحقق ناجحًا، بلا أخطاء runtime أو موارد CSS/JS فاشلة.
- تحقق RTL/LTR وعدم وجود overflow عام في الحالات المستهدفة.

## 7. AD-042 — وضوح الصلاحيات ونطاق الحساب

### الهدف

جعل المستخدم يفهم سبب ظهور أو اختفاء كل وحدة، وما الذي يستطيع تعديله فعليًا.

### التنفيذ

1. إضافة بطاقة نطاق الحساب في مساحة العمل تعرض:
   - الدور الفعلي.
   - الفرع الأساسي والفروع الإضافية.
   - نطاق ملكية السجلات.
   - حالة الحساب إن كانت مراجعة أو إنتاجية.
2. إضافة صفحة أو قسم «صلاحياتي الحالية» للقراءة فقط.
3. عرض سبب عدم الوصول بطريقة آمنة دون كشف صلاحيات داخلية حساسة.
4. إضافة وصف قصير لكل وحدة يوضح نوع الوصول: قراءة، إنشاء، تعديل، اعتماد، أو إدارة شاملة.
5. تمييز الإجراءات التي تحتاج اعتمادًا إضافيًا قبل الإرسال.
6. تحسين شاشة `AccessReviewPage` لتدعم:
   - البحث بالحساب والدور والفرع.
   - عرض مصدر الصلاحية: دور، صلاحية فردية، أو نطاق فرع.
   - تنبيه الصلاحيات الاستثنائية.
   - سجل قبل/بعد عند اعتماد تغيير.
7. عدم منح أو إزالة صلاحيات تلقائيًا في هذه الدفعة.

### معيار القبول

- كل دور تشغيلي يرى فقط الوحدات المسموحة له.
- لا يظهر زر إجراء لا يستطيع المستخدم تنفيذه.
- الوصول المباشر إلى الصفحة أو POST أو REST يظل محميًا خادميًا.
- نجاح مصفوفة الأدوار الأربعة عشر الحالية بالعربية والإنجليزية.

### نتيجة AD-042 — سياق وصول قابل للتدقيق دون تغيير الصلاحيات

اكتملت الدفعة دون منح أو إزالة أي صلاحية، ودون تعديل نطاق أي حساب. تمت إضافة طبقة عرض قراءة فقط في مساحة العمل تعرض الدور الفعال، الفرع الأساسي، الفروع الإضافية، ملكية السجلات، وحالة الحساب، مع قائمة الوحدات المسموحة ونوع الوصول المبسط مثل القراءة، الإنشاء/التعديل، والمراجعة/الاعتماد. لا تعرض هذه الطبقة أسماء القدرات الداخلية، وتبقى حماية الصفحة والإجراء في الخادم كما هي.

كما تم تحسين [AccessReviewPage.php](../wp-content/plugins/auto-dealership-core/src/Admin/AccessReviewPage.php) بفلاتر الحساب والدور والفرع النشط، وإضافة عمود نطاق الفروع مع الحفاظ على تقرير المصدر والسبب ومدة الصلاحية وسجل العمليات الموجود. تم تحسين الترحيل للحفاظ على الفلاتر، مع استخدام نطاق الفروع النشط فقط في العرض والاستعلام.

التحقق بعد التنفيذ:

- مصفوفة الأدوار الفعلية: `872` تحقق ناجحًا، مع عدم وجود overflow أو أخطاء runtime أو موارد فاشلة.
- مراجعة الوصول في المتصفح: `20/20` تحقق ناجحًا، بما في ذلك فلاتر الدور والفرع ونطاق الفروع والملاءمة على 390px ورفض nonce غير صالح.
- عقد الألوان بعد إضافة المكونات: `96/96` في الوضعين الفاتح والداكن وعلى 1440/390px.
- التباين: `0` إخفاقات في المسارات المفحوصة.
- قبول لوحة الإدارة العامة: `162` تحقق ناجحًا.

الملفات الأساسية: [WorkspacePage.php](../wp-content/plugins/auto-dealership-core/src/Admin/WorkspacePage.php)، [admin-workspace.css](../wp-content/plugins/auto-dealership-core/assets/css/admin-workspace.css)، [browser-admin-mobile-roles.cjs](../wp-content/plugins/auto-dealership-core/tests/browser-admin-mobile-roles.cjs)، و[browser-access-governance.cjs](../wp-content/plugins/auto-dealership-core/tests/browser-access-governance.cjs).

## 8. AD-043 — الأداء والتحميل

### الهدف

خفض زمن تحميل الصفحات الثقيلة دون تغيير نتائج الأعمال أو نطاق الصلاحيات.

### التنفيذ

1. تحميل CSS وJavaScript الخاص بالصفحة الحالية فقط.
2. مراجعة hooks التحميل في `Navigation.php` وملفات الإدارة.
3. منع تحميل ملفات CRM والتقارير في الصفحات غير التابعة لها.
4. إضافة pagination وحد أقصى للنتائج في كل جدول كبير.
5. استخدام استعلامات محددة الأعمدة بدل `SELECT *` في التقارير.
6. إضافة فهارس فقط بعد إثبات الحاجة وقياس الاستعلام قبل/بعد.
7. استخدام caching قصير المدى للبيانات التجميعية التي لا تحتاج لحظية كاملة.
8. جعل الفلاتر التاريخية محددة افتراضيًا بمدى زمني معقول.
9. تجنب استدعاء الخدمات نفسها أكثر من مرة في الصفحة الواحدة.
10. إبقاء التصدير خارج مسار العرض التفاعلي عند الحاجة إلى بيانات كبيرة.

### معيار القبول المقترح بعد قياس خط الأساس

- خفض TTFB للصفحات المستهدفة بنسبة لا تقل عن 20% دون بيانات مخزنة.
- عدم تحميل CSS أو JavaScript غير متعلق بالصفحة.
- عدم زيادة عدد الاستعلامات في الصفحات الخفيفة.
- عدم تغيير أرقام التقارير عند مقارنة نفس البيانات والفلاتر.
- عدم ظهور خطأ أو timeout عند جداول كبيرة ضمن الحدود المعتمدة.

### نتيجة الدفعة الأولى من AD-043 — تحميل مشروط بالصفحة

تم تنفيذ دفعة آمنة ومحددة من تحسين الأداء دون تغيير منطق الأعمال أو الصلاحيات:

- أصبح `JobRuntime::assets()` يحمّل مراقب التشغيل في `adc-outbox` فقط، مع بقاء AJAX والتشغيل الخلفي والصلاحيات كما هي.
- أصبح `GroupedModelCatalog` يحمّل أصول النماذج في الإدارة فقط عند محرر سيارة `car` مرتبطة بنموذج منشور، مع إبقاء سلوك الواجهة العامة كما هو.
- أضيفت اختبارات تراجعية تتحقق من عدم تحميل هذه الأصول في `adc-workspace` ومن بقائها فعالة في `adc-outbox`.

القياس الموحد بعد التعديل نجح في `64/64` حالة:

- متوسط TTFB: `143.35ms` ← `139.15ms`.
- متوسط DCL: `642.95ms` ← `643.90ms`.
- متوسط Load: `650.15ms` ← `645.55ms`.
- متوسط النقل: `4,510,782` ← `4,504,579` بايت.
- متوسط عدد الموارد: `88` ← `85`.

تحقق هذا الجزء من خفض الموارد غير المرتبطة بالصفحة، لكنه لم يحقق بعد هدف خفض TTFB بنسبة 20% على مستوى جميع الصفحات؛ لذلك يبقى AD-043 مفتوحًا لاستكمال قياس الاستعلامات، وتحسين الجداول الكبيرة، وتقييم أصول WordPress الأساسية قبل أي تغيير إضافي.

### قياس AD-043 — الاستعلامات والجداول قبل أي تحسين إضافي

تم تنفيذ قياس قراءة فقط على `13` مسارًا إداريًا مستهدفًا باستخدام [admin-query-baseline.php](../wp-content/plugins/auto-dealership-core/tests/admin-query-baseline.php). أُعيد ضبط عداد الاستعلامات لكل صفحة، وحُفظت أشكال الاستعلامات بعد إخفاء القيم، مع تفعيل حارس يمنع أي `INSERT` أو `UPDATE` أو `DELETE` أو DDL أثناء القياس. لم تُسجّل أخطاء عرض أو عمليات كتابة محظورة، ولم يُحفظ SQL خام أو بيانات تعريفية حساسة.

النتائج الحالية من قاعدة التطوير المحلية:

- `platform_readiness`: `157` استعلامًا، وزمن SQL تراكمي `66.791ms`، وزمن عرض `114.625ms`. يتكرر الاستعلام المرتبط بـ `catalog_models` و`onyx_stock` `25` مرة، وتظهر قراءات متكررة لـ `posts` و`postmeta`.
- `crm`: `34` استعلامًا، و`inventory`: `27`، و`settings`: `25`. في `inventory` تظهر قراءات متكررة لـ `posts` و`postmeta`، بينما يقرأ `settings` من `wp_options` عدد `20` مرة.
- `crm_reports`: `21` استعلامًا، لكن زمن SQL هو الأعلى نسبيًا خارج صفحة الجاهزية (`29.915ms`) بسبب استعلامات التجميع وتقارير الحقول؛ يلزم فحص `EXPLAIN` قبل اقتراح فهرس أو إعادة صياغة.
- أكبر الجداول الحالية بحسب الحجم المجمع هي `wp_options`، ثم `wp_adc_audit_events` و`wp_adc_portal_presence` و`wp_adc_request_limits`. حجمها الحالي لا يبرر حذفًا أو ترحيلًا تلقائيًا؛ يلزم أولًا قياس نموها وسياسات الاحتفاظ بها.

حُفظ التقرير الكامل في [query-baseline.json](artifacts/admin-dashboard-performance-baseline-1.66.0/query-baseline.json). هذه قراءة خط أساس من قاعدة التطوير الحالية وليست بعدُ قياسًا معتمدًا لبيانات إنتاج أو نسخة معزولة؛ لذلك لا يُعتمد منها قرار فهرسة قبل إعادة تشغيل الاستعلامات المرشحة مع `EXPLAIN` على نسخة اختبارية مماثلة. دعم التشغيل المعزول موجود في [database-runner.php](../wp-content/plugins/auto-dealership-core/tests/database-runner.php) لإعادة القياس لاحقًا دون لمس قاعدة الموقع.

الخطوة التالية المحددة في AD-043 هي استخراج أفضل الاستعلامات المرشحة من التقرير، تشغيل `EXPLAIN` قراءة فقط، ومقارنة الفهارس الحالية وخطة التنفيذ. بعد ذلك فقط تُنفذ دفعة صغيرة قابلة للعكس، ثم يعاد اختبار الأرقام والصلاحيات والمتصفح قبل الانتقال إلى الاستعلام المرشح التالي.

### نتيجة فحص `EXPLAIN` ومراجعة الفهارس

تم تشغيل [admin-query-explain.php](../wp-content/plugins/auto-dealership-core/tests/admin-query-explain.php) على نفس المسارات وبحارس القراءة فقط. فحص التقرير [query-explain.json](artifacts/admin-dashboard-performance-baseline-1.66.0/query-explain.json) عدد `28` استعلامًا مرشحًا، ونجحت خطط التنفيذ جميعها، وفُحصت فهارس `13` جدولًا، دون تسجيل أي كتابة أو خطأ عرض.

الاستنتاجات القابلة للتنفيذ:

- صفحة الجاهزية تكرر استعلام الطرازات والنسخ المتاحة `25` مرة لكل شكل تقريبًا. هذا عنق زجاجة من نمط N+1، ومعالجته الصحيحة هي تجميع القراءة أو memoization محدد بعمر الطلب، وليس إضافة فهرس عشوائي.
- استعلام مخزون أونكس في صفحة المخزون يقرأ الجدول كاملًا (`523` صفًا محليًا) ويستخدم `Using filesort`. الفهارس الحالية `model_present` و`vehicle_id` مناسبة لعلاقات التصفية الموجودة، لكن ترتيب العرض المركب يحتاج اختبارًا على حجم إنتاجي قبل إضافة فهرس واسع يزيد تكلفة الاستيراد والتحديث.
- استعلام التقييمات العامة هو الأبطأ في العينة (`11.841ms`) ويستخدم الربط بالمفتاح الأساسي مع `temporary/filesort`. فهرس مركب محتمل على حالة الموافقة والحالة والتاريخ يجب اختباره على حجم واقعي؛ لم يُضف لأن الجدول المحلي صغير ولأن الفهرس الحالي `public_version` ما زال مستخدمًا في مسار الربط.
- تقرير أسباب فقدان الفرص يستخدم فهرسًا قائمًا لكنه ينتهي بتجميع وفرز مؤقت. العينة المحلية لا تتجاوز `3` فرص، لذلك لا يوجد دليل آمن بعد على أن إضافة فهرس تاريخي مركب ستعطي مكسبًا يتجاوز كلفته.
- فهارس `public_post_id` و`model_present` و`post_id` و`option_name` والمفاتيح الأساسية استُخدمت في الخطط ذات الصلة. لا يوجد حاليًا فهرس مفقود واضح يبرر migration فورية.

بناءً على ذلك، لا تُنفذ migration أو إعادة صياغة SQL في هذه النقطة. الدفعة التالية الآمنة هي تحسين تكرار قراءة نماذج أونكس على مستوى الطلب فقط، ثم إعادة تشغيل خط الأساس وفحص المتصفح ومقارنة أرقام المخزون والتقارير. إذا لم يكن حجم قاعدة التطوير مماثلًا للإنتاج، يعاد فحص الفهارس على نسخة اختبارية مماثلة قبل أي فهرس دائم.

- لا يؤثر التسجيل على زمن الصفحة بشكل ملحوظ.

### نتيجة تنفيذ AD-046 — مراقبة اختيارية وصحة تشغيلية منقّحة

اكتملت الدفعة الأولى من AD-046 دون إضافة جدول أو migration أو تغيير في صلاحيات الأدوار أو مسارات الحفظ الحالية. أضيفت خدمة AdminDiagnostics اختيارية ومتوقفة افتراضيًا، وتحتفظ في خيار مستقل بحد أقصى 100 سجل ولمدة 7 أيام، مع اعتبار الصفحة بطيئة عند 800ms أو أكثر.

يحتوي السجل التشخيصي على:

- معرف طلب UUID، ومعرف صفحة إداري منقّح، وطريقة الطلب، وحالة الاستجابة، والمدة بالمللي ثانية.
- نوع خطأ PHP واسم الملف فقط عند الحاجة، دون نص الرسالة.
- بصمة أحادية لاتصال قاعدة البيانات عند وجود خطأ، دون SQL أو last_error الخام.
- إشارات آمنة للبطء، مع إبقاء تفاصيل التغيير وبيانات العملاء والاتصالات خارج السجل.

تمت إضافة صفحة adc-diagnostics تحت قسم الرقابة، وتعرض حالة العامل والطابور وإشارات الفشل الموجودة أصلًا في سجل التدقيق. يمكن لمسؤول النظام تفعيل القياس أو تعطيله من الصفحة عبر nonce، كما يمكن قفله من الخادم عبر ADC_ADMIN_DIAGNOSTICS. وتم ربط AuditLog بمعرف الطلب الإداري عند توفره دون تعديل مخطط جدول التدقيق.

التحقق بعد التنفيذ:

- 56 تحققًا فعليًا في المتصفح لصفحة الصحة، مع العربية/الواجهة الحالية، الوضعين الفاتح والداكن، و390/1440px، دون تسريب SQL أو secrets أو overflow.
- 295 تحقق وصولية، و24 مسح axe، وصفر مخالفات بعد إدراج صفحة الصحة في العقد المشترك.
- نجحت فحوص php -l لكل ملفات PHP المعدلة، وفحص JavaScript، وgit diff --check.
- بقي خيار القياس وسجل التشخيص غير موجودين قبل اختبار الصفحة؛ لم تُفعّل الميزة ولم تتغير بيانات الموقع أثناء اختبار القراءة.

## 12. AD-047 — التوثيق ودورة الإصدار

### الوثائق المطلوبة

- دليل الأدوار والصلاحيات.
- دليل التشغيل اليومي لكل دور.
- دليل إدارة الفروع ونطاق الحساب.
- دليل استكشاف أخطاء الداشبورد.
- سجل تغييرات الإصدارات.
- تقرير أداء قبل/بعد كل دفعة.
- تقرير قبول الحزمة النهائي.

### دورة الإصدار الإلزامية

1. تنفيذ دفعة واحدة فقط.
2. فحص `php -l` للملفات المعدلة.
3. فحص JavaScript syntax.
4. تشغيل اختبار الصلاحيات.
5. تشغيل اختبار المتصفح بالعربية والإنجليزية.
6. تشغيل اختبار 320 و390 و768 و1440px.
7. تشغيل اختبار التباين.
8. بناء حزمة ZIP.
9. استخراج الحزمة والتحقق من البصمات.
10. تثبيت الحزمة على WordPress نظيف مع MariaDB معزولة.
11. حفظ النتائج والبصمات في `docs/artifacts/`.
12. مراجعة بشرية على staging قبل الإنتاج.

## 14. استراتيجية التراجع

كل دفعة يجب أن تكون قابلة للتراجع عبر:

- الاحتفاظ بنسخة الحزمة السابقة وبصمتها.
- حفظ diff واضح للملفات.
- عدم تشغيل migrations غير قابلة للعكس دون خطة مستقلة.
- تعطيل الميزة الجديدة خلف flag إن كانت تجريبية.
- إعادة تحميل CSS السابق دون حذف المكونات القديمة حتى اكتمال التحقق.
- الاحتفاظ بنتيجة اختبارات ما قبل التغيير للمقارنة.

إذا فشل اختبار صلاحيات أو ظهر اختلاف في أرقام التقارير، تتوقف الدفعة ولا تنتقل إلى التالية.

## 15. تعريف الإنجاز النهائي

تعتبر الخطة منفذة عندما:

- تنجح كل دفعات AD-040 إلى AD-047 أو يتم توثيق أي استثناء معتمد.
- لا توجد أخطاء PHP أو JavaScript في المسارات المستهدفة.
- تنجح مصفوفة الأدوار والنطاقات واللغات والأحجام.
- تحقق الصفحات المستهدفة أهداف الأداء المثبتة بالقياس.
- تنجح الحزمة في التثبيت والاستخراج والتحديث والتراجع على بيئة معزولة.
- تصبح وثائق الأدوار والتشغيل والإصدار متاحة للفريق.
- تتم مراجعة staging بحسابات مماثلة للإنتاج قبل النشر.

## 17. نتيجة تنفيذ AD-047

تم تنفيذ بوابة التوثيق والإصدار وحفظ الدليل التفصيلي في [ad047-verification.json](artifacts/admin-dashboard-release-1.66.0/ad047-verification.json)، مع إضافة [دليل التشغيل](ADMIN-DASHBOARD-OPERATIONS-GUIDE-AR.md)، و[دليل استكشاف الأعطال](ADMIN-DASHBOARD-TROUBLESHOOTING-AR.md)، و[سجل قبول الإصدار](ADMIN-DASHBOARD-RELEASE-ACCEPTANCE-1.66.0-AR.md).

نتائج التحقق القابلة للتكرار:

- نجح فحص `php -l` لـ19 ملف PHP، وفحص JavaScript لـ9 ملفات، و`git diff --check`.
- نجح اختبار الأدوار عبر المتصفح في 880 تحققًا، واختبار الوصولية في 295 تحققًا و24 مسح axe دون مخالفات، واختبار الألوان في 96 تحققًا، واختبار التشخيص في 56 تحققًا.
