# تشخيص اختبار صفحة إدارة التمويل

20 أكتوبر 2026. النطاق: تتبع فقط دون إصلاح الإنتاج أو تعديل اختبار المصدر.

## السبب الأصلي المثبت

في `tests/browser-finance-admin.cjs:117` ينتظر الاختبار وجود `.notice-success` بعد حفظ الجهة، ثم يستدعي `new FormData(form)` ويفترض وجود `payload` عند السطر 119. رسالة النجاح تظهر أثناء تحليل HTML، قبل سكربت `finance-admin.js` المحمل في تذييل الإدارة.

تكرر القياس مرتين داخل صفحة WordPress الكاملة في نسخة معزولة:

```json
{"ready":"loading","scripts":[],"payload":null}
```

بعد انتظار `document.readyState === 'complete'`، ودون تغيير سكربت الإنتاج، صار `payload` موجودًا واجتاز فحص الإرسال المتكرر: بقي اسم الحقل محفوظًا، وحملت البيانات القيمة الجديدة 5. التجربة الثانية لم تضف نومًا ثابتًا بعد اكتمال الصفحة.

`JSON.parse(null)` يعيد null؛ لذلك قراءة `result.provider` كانت سبب TypeError المذكور، وليست دليلًا على ضياع إعدادات الجهة في قاعدة البيانات. سكربت التحويل لم يكن قد سجل معالج `formdata` بعد.

## إخفاق لاحق كشفه التتبع

عند فحص تعارض تعديل الجهة، ينتظر الاختبار أي `.notice-error` في المستند كله. التتبع التقط تنبيه WordPress العام التالي بدل رسالة الوحدة:

```json
{"ready":"loading","text":"البريد متوقف: يجب ضبط إعدادات SMTP لهذه البيئة. / Mail is disabled: configure SMTP for this environment."}
```

إذن هذا المحدد أيضًا يختبر عنصرًا غير مقصود. رسالة تعارض التمويل نفسها تُعرض داخل `.adc-finance-admin`. الحصر داخل هذه الوحدة وحده لم يكن كافيًا في التجربة التالية: بعد اكتمال الصفحة بقي تنبيه البريد أول `.notice-error` داخلها. يلزم تمييز رسالة العملية نفسها بدل افتراض أن أول تنبيه يخصها.

## الإصلاح المقترح للاختبار

- ربط الانتظار بنتيجة عملية الحفظ والصفحة الجديدة المكتملة، وحصر رسالة النجاح داخل `.adc-finance-admin`، قبل فحص السلوك الذي يحتاج JavaScript.
- انتظار رسالة تعارض العملية نفسها بعد اكتمال الطلب، وعدم افتراض أن أول تنبيه داخل الوحدة يخصها، مع التحقق من بقاء الإعدادات المحفوظة دون الكتابة فوقها.
- عدم الاكتفاء بإضافة مهلة ثابتة أو تجاهل TypeError أو قبول payload فارغ؛ يجب استمرار فحص القيمة الأحدث وأسماء الحقول والحفظ الفعلي.
- مراجعة بقية خطوات `requestSubmit()` في الاختبار لتفادي التقاط رسالة من المستند السابق أو وحدة أخرى.
- لا يلزم تعديل `assets/js/finance-admin.js` أو واجهة الإنتاج لإصلاح السببين المثبتين.

## نطاق البيئة وحماية البيانات

استُخدم PHP 8.2.12 وChrome مع كود الإضافة الحالي ونسخة بيانات محفوظة ومعزولة، على MariaDB المخصص بالمنفذ 33385 وخادم HTTP بالمنفذ 33384. لا اتصال بقاعدة الموقع الأصلي، والبريد معطل. استُعيد خيار إعدادات التمويل وأُتلفت جلسة المتصفح بعد كل تشغيل. تعديلات التتبع تخص نسخة الاختبار داخل `.tmp` فقط. سجلات التتبع في `.tmp/full-audit-20261020/finance-trace.log`، وقد تحتوي بيانات اختبار اصطناعية.

لا تعني هذه النتيجة إثبات عدم وجود أي خلل آخر في التمويل، ولا تمثل تشغيلًا على PHP 8.0 أو الاستضافة أو GitHub Actions.

## نتيجة التحقق النهائي المعزول

بعد إضافة انتظار اكتمال الصفحة وتحديد رسالة التعارض ضمن رسائل الخطأ بدل أول رسالة فقط في **نسخة الاختبار المؤقتة**، نجح المسار الكامل: **19 تحققًا، ورمز خروج المتصفح 0**. ظهر تنبيه البريد ورسالة التعارض معًا؛ رسالة التعارض الصحيحة كانت الثانية. نجحت إضافة الجهة وحفظها وتأثير شرطها في الحاسبة العامة وتكرار التحويل إلى payload وإعدادات التأمين والتعطيل والحذف ورفض nonce غير الصحيح والتعارض والعرض على 390 و1440 وعدم وجود استثناءات أو أصول مفقودة. حُذفت قاعدة النسخة المعزولة بعد انتهاء التشخيص وأُوقف خادم الاختبار.

تحديث التنفيذ: طُبّق الإصلاح في اختبار المصدر، وأضيف التحقق من بقاء مراجعة الإعدادات بعد رفض الحفظ. اجتاز المسار 21 تحققًا دون تغيير كود حفظ التمويل. النتيجة الحالية موثقة في [تقرير الإصلاحات والتحقق](COMPREHENSIVE-REPAIRS-VALIDATION-AR.md).
