# خطة إصلاح إخفاقات الاختبارات والواجهة

هذه وثيقة التشخيص والخطة قبل التنفيذ. نتائج التنفيذ والتحقق الأحدث في [تقرير الإصلاحات](COMPREHENSIVE-REPAIRS-VALIDATION-AR.md).

تاريخ المراجعة: 20 أكتوبر 2026. النطاق: فحص وخطة فقط؛ لا إصلاحات إنتاج أو تغييرات بيانات.

## الأدلة وحدود الاستنتاج

راجعت ملفات الإنتاج والاختبارات وسجلات الفحص الشامل المحفوظة في `.tmp/full-audit-20261020/`. الفحص السابق شغّل PHP 8.0.30 و8.2.12 فعليًا، بما فيه اختبارات قواعد البيانات وحزم ZIP والمتصفح والترقية والاسترجاع. لا يمثل ذلك نجاح GitHub Actions أو اختبار الاستضافة.

في هذه المراجعة أعدت اختبار الترجمة المستقل وفاحص كتالوج الترجمة على PHP 8.2، وأجريت تجربة Chrome منفصلة على سكربت إرسال نموذج التمويل الحالي دون WordPress أو قاعدة بيانات. لم أعد تشغيل الحزمة الشاملة، ولم أعد إنتاج مهلة PHP 8.0 بأداة تتبع شبكة جديدة. الأسباب غير المحسومة أدناه تبقى أعمال تشخيص، ولا يجوز تغيير كودها بالتخمين.

## النتائج حسب المجال

### 1. رفض رابط عميل خارج النطاق — خلل إنتاج مؤكد في توقيت الرفض

- `src/Admin/CustomerWorkspacePage.php:26` يخرج عنوان الصفحة قبل حساب السجلات المرئية؛ الرفض 404 يأتي عند السطر 57.
- `boot()` يسجل callback العرض دون فحص `load-$hook`. و`Navigation.php` يسجل مدخل الصفحة أيضًا؛ يلزم تغطية التسجيل الفعلي النهائي وجميع المداخل، وليس أول تسجيل فقط.
- نقل الرفض إلى أول `render()` وحده لا يضمن صحة HTTP لأن WordPress قد يخرج ترويسة الإدارة قبل استدعاء callback.
- اسم العميل لا يُقرأ ويُعرض إلا بعد فحص الرؤية؛ لا يوجد في هذا الدليل إثبات تسريب بيانات العميل.

الإصلاح المخطط: مشاركة منطق استخراج السجلات المسموح بها بين التحقق المبكر والعرض، وإضافة حارس قبل ترويسة الإدارة عبر `load-$hook` مع حماية مباشرة عند استدعاء `render()`. الحفاظ على شروط الفرع والمالك والقدرات المالية كما هي. تجنب مضاعفة كل استعلامات الأقسام بين الحارس والعرض؛ يمكن مشاركة نتيجة مرتبطة بطلب الصفحة الحالي فقط. عدم تحويل رفض النطاق إلى بحث غير مقيد عن وجود العميل.

القبول: 404 للعميل الغائب أو خارج النطاق، 403 لمن لا يملك صلاحية القراءة، 200 للمسموح؛ دون اسم أو سجلات أو نماذج العميل الأجنبي؛ مع بقاء الأقسام المالية محكومة بقدراتها. الاختبار عبر مسار WordPress الإداري الحقيقي ومع `output_buffering=0` على الإصدارين، مع فحص القائمة والترقيم والمستخدم متعدد القدرات.

### 2. عرض الكسور بالمخزون — عدم تطابق مؤكد بين تجهيز الاختبار ومسار العرض

- `browser-currency.cjs:99` يتوقع `1234.56` و`2345.67` في الصفحة الافتراضية.
- `currency-scenarios.php` و`currency-lifecycle.php` ينشئان هذين السعرين في جدول السيارات التشغيلية.
- `tests/http-router.php:74` يستدعي `OperationsPages::render()` دون `legacy`.
- `OperationsPages::render()` يحول افتراضيًا إلى `InventoryWorkspacePage::render()`؛ السجلات التشغيلية القديمة متاحة عبر `legacy=1`.
- الوحدة الجديدة تقرأ من `onyx_stock`، وتعرض `listed_price` وسعر الموقع المحسوب، وليس `vehicles.retail_price` مباشرة. كلا العرضين يستخدمان `Money::display()`.
- اختبار PHP للعرض نفسه يضبط `$_GET['legacy']='1'`، وهو فرق صريح عن اختبار المتصفح.

الإصلاح المخطط: تقسيم التحقق إلى عرض السجلات التشغيلية مع السعرين الحاليين، وعرض مخزون أونكس ببيانات أونكس اصطناعية وأسعار الموقع المحسوبة. استهداف صفوف السيارات بمعرف ثابت بدل البحث في كل نص الصفحة. اختبار العربية والإنجليزية والضرائب والرسوم دون تغيير الحسابات أو إعادة خلط مصادر الأسعار لإرضاء الاختبار.

القبول: ظهور الكسور الصحيحة في كل صفحة وفق مصدر سعرها؛ لا ظهور للوحدات الصغرى الخام، ولا تحويل مزدوج عند الحفظ، واستمرار اجتياز الحسابات والتسوية والاسترداد والطباعة والتصدير.

### 3. الترجمة — مشكلتان منفصلتان مؤكدتان

`tests/localization.php` لا يحمل `ProductSetup` أو autoloader رغم استدعاء `Localization::gettext()` له. أعدت الفشل على 8.2. الإصلاح في تجهيز الاختبار: تحميل الاعتماد الحقيقي وما يحتاجه من stubs محددة، أو bootstrap اختبارات مشترك محدود؛ لا إضافة تجاوز داخل الإنتاج لإخفاء غياب الكلاس، ولا تحميل قاعدة الموقع الأصلي.

فاحص `tools/check-ui-localization.php` أعاد 11 سجل نقص تخص `Navigation.php` و`OutboxPage.php`، تمثل 10 عبارات فريدة لأن وصف النقل يتكرر في سياقين. الإصلاح في كتالوج الترجمة المعتمد، مع الحفاظ على مفاتيح الحالات والبيانات المخزنة وأسماء القدرات دون ترجمتها أو تعديلها. يجب بقاء فحص النصوص إلزاميًا وعدم إضافة استثناءات لهذه العبارات.

القبول: نجاح الاختبار المستقل على 8.0 و8.2، صفر سجلات نقص، والتحقق من لغة الإدارة المستقلة عن لغة الواجهة وطلبات AJAX، مع بقاء الأسماء والمحتوى المجهول دون تحريف.

### 4. مهلة الحساب والاستعادة والبوابة على PHP 8.0 — السبب لم يُحسم

السجلات تثبت انتهاء `page.goto` عند انتظار `load` على خادم PHP CLI المضمن في Windows. نجاح 8.2 والاختبارات الخلفية لا يستبعد مشكلة إنتاج. سجلات الخادم الحالية لا تربط كل اتصال بمعرف طلب ومسار وزمن تنفيذ، لذلك لا تفصل بين الطلب الرئيسي وملف تابع أو اتصال معلق.

خطوة تشخيص إلزامية قبل الإصلاح:

1. تثبيت نفس الحزمة والبيانات والمتصفح والإضافات والإعدادات على الإصدارين في بيئة معزولة، وتشغيل الحالات منفردة دون تنافس على الخادم.
2. تسجيل الطلبات والتحويلات والاستجابات والطلبات الفاشلة وتوقيت `DOMContentLoaded` و`load`، وحفظ trace وHAR بعد تنقيح cookies وكلمات المرور وnonces وروابط استعادة الحساب.
3. مقارنة الطلب الرئيسي عبر curl دون المتصفح ومعه؛ قياس أول بايت واكتمال الجسم، ثم ربط ذلك بسجل PHP والاستعلامات والطلبات الداخلية. التحقق من الملفات المعلقة والاتصالات المسبقة والخادم أحادي العامل والطلبات التي تستدعي الخادم نفسه، دون افتراض أيها سبب مثبت.
4. إعادة الحالة على Apache/FastCGI معزول بالإصدار نفسه لتمييز سلوك خادم الاختبار عن التطبيق. لا تغيير خادم الموقع الأصلي أو إعداداته.
5. إن كان السبب في الاختبار، إصلاح خدمته أو انتظار جاهزية الصفحة المطلوبة مع استمرار التحقق من اكتمال الملفات والوظيفة؛ إن كان في الكود، إصلاح موضع التعليق المثبت فقط.

القبول: نجاح الحساب والاستعادة والبوابة والحزمة العامة على 8.0 و8.2 دون رفع مهلة الانتظار لمجرد إخفاء الفشل، ودون إسقاط انتظار ضروري أو تجاهل أخطاء الأصول. تكرارات تشخيصية موثقة للحالة المتقطعة، ثم الحزمة الكاملة بعد الإصلاح.

## ترتيب التنفيذ المقترح

1. **تثبيت خط أساس وتجهيزات صحيحة:** حفظ commit وdiff والملفات والبيانات المعزولة؛ تحسين أدلة الفشل وإصلاح الراوتر والـfixtures القديمة. إبقاء فشل الإنتاج ظاهرًا وعدم تحويل إعادة التشغيل إلى نجاح صامت.
2. **رفض الوصول المبكر:** تغيير صغير مستقل في ملف العميل وتسجيل مداخله، مع اختبارات HTTP والصلاحيات أولًا.
3. **الترجمة وتغطية العملة:** إصلاح الاعتماد وكتالوج العبارات، وفصل اختبار المخزون التشغيلي عن أونكس. لا تغيير وحدة التخزين أو الحسابات.
4. **تشخيص مهلة 8.0:** حسم الشبكة/الخادم/الكود بالأدلة قبل اختيار الإصلاح. لا تُقبل الحزمة للنشر مع بقاء المسارات غير مختبرة بسبب المهلة.
5. **استكمال عقود الواجهة:** التخصيص والتمويل والصلاحيات والنشر، ثم المحاذاة والعناوين. كل عيب أو تحديث اختبار في تغيير مستقل قابل للمراجعة.
6. **التباين:** تعديلات مكونات محددة وإعادة التحقق البصري والآلي.
7. **التحقق النهائي:** المستقلة، وجميع أوضاع قاعدة البيانات، ورحلات المتصفح والحزم، والترقية والاسترجاع على 8.0 و8.2، ثم GitHub Actions بعد الرفع المصرح به.

## حماية الوظائف والبيانات ومعايير الإغلاق

- لا حذف صفحات أو slugs أو shortcodes أو REST routes أو قدرات؛ فحص التسجيل والوصول والتحويلات الحالية بدل تعداد النصوص داخل ملف بعينه.
- لا schema migrations أو حذف بيانات أو إعادة استيراد أونكس ضمن هذه الإصلاحات دون سبب مستقل مثبت؛ الخطة الحالية لا تحتاج ذلك.
- كل اختبارات الكتابة في قواعد ووسائط منفصلة، مع بريد loopback فقط، وعدم تحميل `wp-load.php` الخاص بالموقع الأصلي.
- الاحتفاظ بحد الاستعلامات 25 وبنتيجة الأساس 19 كمرجع؛ المحافظة على نطاق الفرع والمالك والعزل بين حساب العميل والموظف والمدير.
- إعادة اختبارات الدخول والتسجيل وتأكيد البريد واستعادة كلمة المرور والتحويلات والمظهر والتمويل والمخزون والتسويات والصلاحيات عند التغييرات ذات الصلة، ثم تشغيل الحزمة الكاملة مرة نهائية.
- منع `continue-on-error` وإخفاء رموز الخروج وتعطيل الاختبارات وتحويل private إلى public لإرضاء اختبار.
- إخراج تقرير لكل مرحلة: السبب، الملفات، الاختبارات ونتائجها، أثر السلوك وخطة الرجوع. الرجوع لتغييرات المرحلة فقط، دون إسقاط تعديلات المستخدم أو البيانات التي أنشئت لاحقًا.
- لا يمكن ضمان انعدام الانحدارات مسبقًا؛ يتحقق القبول بالأدلة والاختبارات ومراجعة diff واسترجاع موثق، لا بعبارة ضمان عامة.
